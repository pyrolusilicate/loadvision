# Как устроен Loadvision

Документ объясняет устройство сервиса и причины принятых решений. Запуск описан в
`running.md`, ML-цепочка по файлам в `ml/pipeline.md`.

## Картина целиком

Сервис принимает фотографию кузова и номер перевозки в XML, оценивает загрузку от 0 до 100
процентов, сохраняет оценку и отдает ее по номеру перевозки. Оператор подтверждает настоящую
загрузку или помечает кадр непригодным, и эти метки идут в дообучение.

Код разложен по слоям, а правило проверяет import-linter на каждом запуске проверок.

```
api | cli  ->  infrastructure | ml  ->  application  ->  domain
```

| Слой | Что в нем |
|---|---|
| `domain` | перевозка, оценка, метка, версия модели и их правила |
| `application` | сценарии и порты, описанные протоколами |
| `infrastructure`, `ml` | Postgres, файлы, модель, пайплайн |
| `api`, `cli` | входные точки, то есть XML API, страницы оператора и команды, плюс сборка зависимостей |

Отдельно стоят общие модули `errors.py` с каталогом ошибок, `settings.py`, `imaging/` для
проверки и подготовки фотографий и `observability/`.

## Сущности

| Сущность | Где | Правила, которые она держит |
|---|---|---|
| `ShipmentId` | `domain/shipment.py` | формат номера, от 1 до 64 латинских букв, цифр, `_` и `-`. Та же строка повторена в XSD, и тест сверяет обе копии |
| `Shipment` | там же | номер и время появления. Перевозка создается первой оценкой |
| `LoadPercent` | `domain/assessment.py` | загрузка от 0 до 100, конечное число. NaN и бесконечность отвергаются до сравнений |
| `Signals` | там же | неуверенность, непохожесть на обучающие кадры, яркость, резкость. Каждый сигнал либо неотрицательное число, либо отметка «не считали» |
| `ReviewReason` | там же | причина ручной проверки, одна из `low_confidence`, `unusual_scene`, `too_dark`, `blurry` |
| `Assessment` | там же | оценка фотографии в перевозке с загрузкой, версией модели, временем счета, сигналами, причинами и идентификатором запроса. Признак `needs_review` не хранится, а выводится из причин |
| `ConfirmedLabel` | `domain/confirmed_label.py` | вердикт о фотографии, загрузка либо отметка «непригодна». Повтор заменяет вердикт, время первой метки сохраняется. Обычно это вердикт человека, а источник `model` означает нечитаемый кадр, забракованный сервисом |
| `Weighing` | `domain/weighing.py` | сколько весит груз на фотографии, то есть выбранный кузов, его габариты, вид груза и сам ответ вилкой. Принадлежит оценке, а не фотографии, поскольку один кадр в другой перевозке может стоять в другом кузове, а кузов задает объем |
| `ModelVersion` | `domain/model_version.py` | версия пакета, ее статус и разрешенные переходы |
| `ImageRecord` | `application/ports.py` | описание фотографии, то есть sha256, формат и размеры. Байты лежат в хранилище |
| `PreparedImage` | `imaging/prepared_image.py` | декодированная фотография, исходные байты, пиксели RGB и sha256, посчитанный тут же |
| `Operator` | `domain/operator.py` | аккаунт страниц оператора, логин строчными буквами, хэш пароля, признак включенности, счетчик неверных паролей в текущем окне |
| `OperatorSession` | там же | вошедший браузер, sha256 токена, логин, CSRF-токен форм и срок жизни |

Три решения в этой таблице экономят много сил дальше.

- **Загрузка хранится как есть, без округления.** Округление это представление, поэтому XML
  пишет один знак после точки, а база хранит точное число. Иначе повторные округления
  накапливались бы.
- **Метка принадлежит фотографии, а не оценке.** Один кадр может попасть в несколько перевозок,
  и подтвержденная загрузка от этого не меняется. Поэтому метка видна во всех оценках этой
  фотографии, а в дообучение кадр попадает один раз.
- **Взвешивание принадлежит оценке, а не фотографии**, ровно по обратной причине. Вес зависит
  от кузова, а кузов у каждой перевозки свой.

## Хранение, инварианты держит база

Файл `infrastructure/db/tables.py` задает эталон схемы, а `migrations/versions/` содержит шаги,
которыми схема доводится до этого состояния. Интеграционный тест сравнивает мигрированную базу
с таблицами из кода, разойтись они не могут.

| Таблица | Ключевые ограничения |
|---|---|
| `images` | ключом служит sha256, формат берется из списка, размеры положительные |
| `shipments` | ключом служит номер, формат проверяется `CHECK` по тому же шаблону, что и в домене |
| `assessments` | `UNIQUE (shipment_id, image_sha256)`, загрузка в пределах 0-100, причины проверки только из известного списка |
| `confirmed_labels` | одна метка на фотографию, `CHECK (load_pct IS NULL) = unusable`, источник из списка, `updated_at >= created_at` |
| `model_versions` | частичный `UNIQUE`, активная версия ровно одна, время активации согласовано со статусом |
| `training_jobs` | частичный `UNIQUE`, одновременно выполняется одна задача обучения |
| `operators` | ключом служит логин, формат по тому же шаблону, что в домене, счетчик неверных паролей согласован с началом окна |
| `operator_sessions` | ключом служит sha256 токена, а не сам токен. Логин ссылается на аккаунт, сессия кончается позже, чем начинается |

Списки допустимых значений в `CHECK` собираются из доменных перечислений прямо в коде таблиц,
поэтому новый статус или причина не могут появиться в домене и не появиться в базе.

Инварианты живут в базе, а не в коде, по простой причине. Правила «одна активная модель» и
«одно обучение за раз» должны держаться при двух процессах и при гонке. Код способен их только
соблюдать, а база гарантировать.

**Числа с плавающей точкой.** Postgres ставит NaN выше любого числа, поэтому `CHECK (x >= 0)`
пропустил бы NaN. Диапазоны написаны так, чтобы NaN и бесконечность отсекались, то есть
`x >= 0 AND x <= 100`, а для неотрицательных величин `x >= 0 AND x < 'Infinity'`.

## Порты и репозитории

Файл `application/ports.py` описывает, что сценарию нужно снаружи. Это репозитории перевозок,
оценок, фотографий, версий модели и меток, хранилище фотографий, предиктор и единица работы.
Все они протоколы, а не классы, и реализация подставляется снаружи.

Абстракция стоит недорого. Все шесть репозиториев на Postgres занимают около 400 строк
SQLAlchemy Core, фейковые в памяти столько же. Взамен получается следующее.

- **Тесты без базы.** Полторы тысячи быстрых тестов проходят за полминуты на фейках в памяти,
  а интеграционные тесты на настоящем Postgres вынесены в отдельный набор.
- **Одни и те же тесты для обеих реализаций.** Набор `tests/port_contracts/` проверяет
  поведение и на фейке, и на Postgres. Фейк не может разойтись с базой незаметно, и если
  реализация в памяти умеет то, чего не умеет Postgres, красный тест это покажет. Фейк даже
  повторяет частичный уникальный индекс, поэтому попытка активировать вторую версию падает и в
  памяти.
- **Замена без правки сценариев.** Сборка приложения с настоящей базой не потребовала ни одной
  правки в `application/`.

Выбран SQLAlchemy Core, а не ORM, потому что нужны ровно те запросы, которые написаны. ORM
добавила бы ленивую загрузку, кеш сессии и неожиданные `SELECT` в цикле. Core дает
типобезопасную сборку SQL и явные запросы.

**Единица работы** в лице `PostgresUnitOfWork` это одна транзакция на один сценарий.

```python
with self.uow_factory() as uow:  # взяли соединение из пула, началась транзакция
    uow.assessments.add(assessment)  # изменения видны только внутри
    uow.commit()  # сохранили
# выход без commit или с исключением откатывает все, соединение возвращается в пул
```

Две ловушки здесь закрыты тестами.

- **Повтор фотографии не ловится исключением.** Нарушение уникальности обрывает всю транзакцию
  в Postgres, а порт обещает, что после повтора единицей работы можно пользоваться дальше.
  Поэтому вставка оценки идет через `INSERT ... ON CONFLICT DO NOTHING RETURNING id`, и если
  ничего не вернулось, оценка уже есть.
- **Поле `rowcount` у SQLAlchemy Core на psycopg равно -1** для `insert()`, хотя у самого
  psycopg оно верное. Поэтому факт вставки проверяется через `RETURNING`, а не по числу строк.

## Идемпотентность

Дубли блокируются не полем в запросе, а содержимым фотографии.

1. Фотография узнается по `sha256` своих байтов. Клиенту не нужен ключ идемпотентности, потому
   что одна и та же фотография это одна и та же фотография.
2. В базе стоит `UNIQUE (shipment_id, image_sha256)`. Второй такой пары не будет физически.
3. Сценарий сначала читает. Если оценка этой пары уже есть и ее дала та версия модели, которая
   отвечает сейчас, он возвращает ее и не запускает модель. В ответе появляется `reused="true"`
   и статус 200 вместо 201.
4. Если оценку дала другая версия, фотография считается заново, и новая оценка заменяет строку.
   У перевозки одна оценка на фотографию, поэтому идентификатор и адрес карточки сохраняются.
   В ответе появляется `reused="false"` и статус 201.
5. Если та же фотография пришла в другой перевозке, создается новая оценка, но прогноз берется
   из старой по паре «sha256, версия модели». Модель второй раз не считает.
6. Если параллельный запрос успел закоммитить первым, наш вставит ничего, прочитает его оценку
   и вернет ее как повтор. Это проверено интеграционным тестом с двумя потоками.

Фотография в хранилище лежит по своему хэшу, поэтому повторная присылка не создает второй файл.
Запись на диск идет через временный файл с переименованием, и читатель никогда не увидит
недописанный кадр.

Порядок записи выбран намеренно, сначала файл, потом база. Если упадет база, останется лишний
файл, а при обратном порядке осталась бы запись без фотографии.

## XML-контракт

Одна схема `api/xsd/loadvision-v1.xsd` описывает все сообщения и отдается клиенту по адресу
`GET /api/v1/schema.xsd`. Форматы, которые живут еще и в коде, а именно номер перевозки, версия
модели, коды ошибок, причины проверки, форматы файлов и идентификатор запроса, повторены в схеме
намеренно, и тест сверяет обе копии.

Разбор запроса устроен так.

- Парсер создается заново на каждый документ, без DTD, без внешних сущностей и без сети, поэтому
  классическая атака XXE не проходит. Объявление `DOCTYPE` отклоняется отдельно.
- Документ проверяется по XSD до того, как код что-то из него читает.
- Ошибка XSD переводится в код. Претензия только к `ShipmentId` дает `INVALID_SHIPMENT_ID`,
  только к `Image` дает `INVALID_ENCODING`, во всех прочих случаях получается `INVALID_XML`.
  В подробности для лога попадают только имена элементов, поскольку сообщение libxml2 может
  процитировать значение, а значение `Image` это все фото целиком.
- Base64 декодируется строго еще раз, потому что libxml2 проверяет его нестрого и пропускает
  префикс `data:image/jpeg;base64,`. Пробелы и переносы строк разрешены, так base64 переносят
  Java, openssl и почтовые кодировщики.
- Размер тела проверяется до чтения. Если заявленный `Content-Length` больше лимита, ответ 413
  приходит, не прочитав ни байта, а потоковое тело читается в память до лимита и обрывается.

В ответах есть два правила, о которых стоит помнить.

- Элемент `Review` пишется, только когда есть причины. Поэтому пустой набор не означает
  «проверено», и признак `needed="false"` утверждал бы больше, чем сервис знает. Какие причины
  сервис выставляет и по какому правилу, описано в [features.md](features.md).
- Метка фотографии приходит либо загрузкой, либо пустым элементом `Unusable`. Схема запрещает
  оба сразу и запрещает ни одного, поэтому брак с загрузкой 70 невозможен на уровне контракта.

## Каталог ошибок

Один каталог `errors.py` обслуживает API, пайплайн и логи. У кода есть HTTP-статус, сообщение и
подсказка на русском. Тексты не содержат чисел лимитов и форматов, поскольку лимиты живут в
конфигурации, а формат номера в домене и XSD, иначе копии разошлись бы.

| Код | HTTP | Когда |
|---|---|---|
| `INVALID_CONTENT_TYPE` | 415 | тело не `application/xml` |
| `INVALID_XML` | 400 | не разбирается, не проходит схему, содержит DOCTYPE |
| `INVALID_SHIPMENT_ID` | 400 | номер перевозки не того формата |
| `INVALID_ENCODING` | 400 | фотография не в строгом base64 |
| `TRAINING_MODE_NOT_SUPPORTED` | 400 | попросили полное дообучение, очередь умеет только быстрое |
| `PAYLOAD_TOO_LARGE` | 413 | тело или фотография больше лимита |
| `UNSUPPORTED_FORMAT` | 415 | файл не JPEG, не PNG и не WebP. Формат HEIC узнается и называется явно |
| `CORRUPTED_IMAGE` | 422 | не декодируется, обрезан, слишком мал или слишком много пикселей |
| `SHIPMENT_NOT_FOUND` | 404 | нет такой перевозки |
| `ASSESSMENT_NOT_FOUND` | 404 | нет такой оценки или идентификатор не каноничный |
| `MODEL_VERSION_NOT_FOUND` | 404 | версия не зарегистрирована или откатываться не на что |
| `TRAINING_JOB_NOT_FOUND` | 404 | нет такой задачи дообучения |
| `ROUTE_NOT_FOUND` | 404 | нет такого адреса |
| `METHOD_NOT_ALLOWED` | 405 | не тот метод, ответ несет заголовок `Allow` |
| `TRAINING_ALREADY_RUNNING` | 409 | дообучение уже в очереди или выполняется |
| `MODEL_VERSION_STATUS_CONFLICT` | 409 | запрещенный переход статуса версии |
| `MODEL_NOT_READY` | 503 | модель еще не загрузилась |
| `MODEL_INFERENCE_FAILED` | 500 | модель упала или вернула значение вне 0-100 |
| `STAGE_CHECK_FAILED` | нет | постусловие этапа пайплайна, клиенту не показывается |
| `MODEL_PACKAGE_INVALID` | нет | пакет модели не прошел проверку |
| `INTERNAL_ERROR` | 500 | все остальное, без подробностей наружу |

Три правила делают ошибки безопасными. Подробности из поля `detail` идут только в лог, в ответе
их нет. Код без HTTP-статуса никогда не уходит клиенту как есть, он превращается в
`INTERNAL_ERROR`. В каждом ответе есть `requestId`, по которому запрос ищется в логах.

Задача дообучения хранит не только решение гейта, но и его причину одной строкой в поле
`training_jobs.gate_reason`. Отказ без чисел был бы оракулом, с которым нельзя ничего сделать.

## Фотографии, одна дверь для всех

Модуль `imaging/validator.py` это единственный путь от байтов к пикселям, и для сервиса, и для
обучения. Порядок проверок выбран так, чтобы дорогие шаги шли после дешевых. Сначала пустой
файл, затем размер, затем сигнатура формата по содержимому, затем размеры из заголовка до
распаковки пикселей, и только потом полное декодирование.

Полное декодирование обязательно, потому что `verify()` у Pillow пропускает обрезанные файлы.
Поворот по EXIF и перевод в RGB делаются ровно так же, как это делает обучение, поэтому модель
в сервисе видит то же изображение, что видела при обучении.

Пиксели после декодирования помечаются только для чтения. Члены ансамбля читают одно и то же
изображение, и если бы один из них нормализовал его на месте, следующий получил бы испорченный
вход. Теперь такая попытка падает сразу.

## Модель это сущность со статусами

Модель поставляется пакетом, то есть папкой с `manifest.json` и файлами весов. Манифест
описывает версию, членов ансамбля с их энкодером, рантаймом, файлом головы, весом и
препроцессингом, цепочку постобработки, коммит кода, хэш датасета и sha256 каждого файла. При
загрузке хэши проверяются, поэтому подмененный или недокачанный файл до сервиса не дойдет.

**Веса энкодеров лежат в пакете, и сервис читает их оттуда** через
`ml/packaging/checkpoints.py`. Пакет хранит нетронутый чекпойнт timm каждого энкодера, а
предиктор передает timm путь к этому файлу, а не имя для скачивания. Поэтому сервису не нужна
сеть, и работает ровно тот файл, хэш которого проверил пакет. Если бы энкодер скачивался по
имени, обновление чекпойнта на Hugging Face тихо поменяло бы прогнозы. Чекпойнты публичные и
весят около гигабайта, поэтому пакет может передаваться и без них, а команда `model fetch`
скачивает каждый по имени и принимает, только если хэш совпал с манифестом.

Версии живут в таблице `model_versions` со статусами и разрешенными переходами.

```
candidate --> active --> retired --> active   (откат, возвращаем ту, что уже работала)
    \--> rejected                             (тупик, отвергнутую не активируют)
```

Переходы проверяет домен, единственность активной версии гарантирует база. Время активации и
статус согласованы еще одним `CHECK`.

Те же действия доступны в API через `GET /api/v1/models` и
`POST /api/v1/models/{версия}/activate`. Версиями управляют три команды. Команда
`model register` кладет пакет в папку моделей и записывает версию кандидатом, `model activate`
включает ее и отправляет прежнюю в отставку, `model rollback` возвращает ту, что работала до
текущей. Регистрация и активация разделены намеренно, поскольку пакет может существовать и не
отвечать на запросы.

При старте и при каждой последующей сверке сервис делает четыре шага
(`application/load_served_model.py`, `ml/inference/model_follower.py`).

1. Спрашивает базу, какая версия активна.
2. Если активной нет, берет начальную версию из настроек.
3. Грузит пакет и проверяет, что манифест объявляет ту же версию.
4. Только после успешной загрузки записывает версию в базу как активную.

Поэтому сломанный пакет не становится активной версией, а каждая сохраненная оценка ссылается
на существующую запись версии. Пока модель грузится, сервис уже отвечает, чтение работает, а
оценка дает 503. Загрузка идет в фоновом потоке, прогнозы выполняются по одному, поскольку
torch-модель не рассчитана на одновременные вызовы, а один прогноз получает все ядра.

Запрос, который взял модель, досчитывает на ней, даже если в этот момент активировали другую.
В оценке записана версия, которая ее действительно сделала.

**Как сервис узнает о новой версии.** Какая версия активна, решает только база. Команда, API,
страница и воркер меняют запись там, а каждый процесс сервиса раз в `model.check_seconds`
сравнивает активную версию с той, которой отвечает, и при расхождении грузит ее в фоне. Так
переходят все реплики, и никому не нужно знать, где они запущены. Выбран опрос, а не
`LISTEN/NOTIFY` Postgres, потому что это один дешевый запрос раз в несколько секунд и ни одного
постоянного соединения, которое надо переподключать. API и кнопки на странице запускают сверку
сразу, чтобы не ждать очередной. Версию, пакет которой не загрузился, сервис пробует снова
только через `model.retry_seconds`, поэтому сломанный пакет не перечитывается на каждой сверке,
а пакет, положенный позже, подхватывается сам. Одновременно идет одна загрузка.

## Дообучение и защита от деградации

Метки оператора превращаются в модель-кандидата, кандидат проходит проверку, и по ее итогу он
либо активируется, либо отклоняется. Устройство самого обучения описано в
[ml/model.md](ml/model.md).

От деградации защищают шесть вещей.

- **Фолды никогда не меняются.** Файл `configs/splits/folds.json` лежит в git, а команда сборки
  отказывается его перезаписать, если хоть одна фотография поменяла бы фолд. Иначе сравнение
  версий между собой ничего не значило бы.
- **Оценка модели считается только вне обучения.** Каждая фотография предсказывается моделью,
  которая ее не видела и вместе с ней не видела других кадров того же кузова, поскольку фолды
  держат сцену целиком.
- **Прогноз старой модели уже сохранен.** В таблице `assessments` записаны загрузка и версия
  модели. Когда появляются новые подтвержденные фотографии, кандидата можно сравнить с
  действующей моделью на тех же кадрах, ничего не пересчитывая.
- **Постобработка подгоняется вне фолда.** Порог или кривая никогда не видят фотографий, на
  которых их судят, иначе выигрыш оказался бы нарисованным.
- **Разброс по фолдам считается и показывается.** Улучшение меньше разброса не считается
  улучшением.
- **Пакет проверяется при загрузке.** Хэши файлов, поддерживаемый рантайм и пробный прогон на
  пустом кадре приводят к тому, что несовместимая голова падает при загрузке, а не на первом
  запросе клиента.

**Как устроена очередь.** Задача это строка в `training_jobs` со статусами
`queued -> running -> succeeded | failed`. Воркер работает тремя короткими шагами, между
которыми не держит транзакцию. Он берет задачу, обучает и записывает исход.

- Задачу берут запросом `SELECT ... FOR UPDATE SKIP LOCKED`, поэтому второй воркер не ждет
  занятую строку, а проходит мимо нее.
- Пока одна задача выполняется, новая не берется, и частичный уникальный индекс держит то же
  правило в базе.
- Обучение идет вне транзакции, поскольку длится минуты, и соединение с базой не должно его
  ждать.
- Если воркер падает на задаче, она записывается неудачной до того, как исключение полетит
  наверх. Иначе она осталась бы выполняющейся навсегда и закрыла бы очередь.
- Отвергнутый гейтом кандидат это успешная задача, потому что обучение отработало, а гейт
  сделал свою работу. Версия регистрируется, но не включается.
- Пакет кандидата попадает в папку моделей и регистрируется до активации, поэтому включается
  только то, что сервис действительно может загрузить.

## Оценка веса груза

Фотография говорит, какая доля пола занята, и больше ничего из того, что нужно весу. Размер
кузова с нее снять нельзя, поскольку в кадре нет предмета известного размера, от которого
считался бы масштаб. Плотность груза тем более. Поэтому обе величины выбирает оператор, а ответ
идет вилкой.

Считается произведение четырех множителей, а именно площадь пола, доля занятого пола, доля
высоты штабеля и плотность. Первый берется из справочника кузовов, второй от модели, третий
равен константе 0.6, четвертый берется из таблицы плотностей по виду груза. Арифметика живет в
`domain/cargo_weight.py`, она чистая и покрыта тестами.

**Плотности это допущения, а не замеры.** Весов в датасете нет вовсе, поэтому ни MAE, ни какой
бы то ни было точности у оценки веса не существует. Числа и проверка на здравый смысл приведены
в [features.md](features.md).

**Взвешивание хранится, а не считается на каждый показ.** Таблица плотностей может поменяться,
а число, по которому оператор принял решение, меняться под ним не должно. Поэтому в таблице
`weighings` лежат и входные данные, и ответ. По первым видно, из чего число собрано, вторые
фиксируют, что именно человек видел в тот день.

Эта возможность не участвует в прогнозе, не меняет XML-ответ и не вызывает модель. Это отдельная
форма под фотографией, отправляющая POST, и страница без нее работает как работала.

## Страницы оператора

Страницы живут в том же процессе, что и XML API. Это подприложение FastAPI на `/ui` с шаблонами
Jinja2 в папке `api/ui/`. Они вызывают те же сценарии, что и API, и отличаются только ответом,
то есть HTML вместо XML. JavaScript отсутствует полностью, форм и переходов хватает, собирать
нечего. Список страниц приведен в `running.md`.

Вход устроен так.

- **Аккаунты заводит только командная строка** через `loadvision operators`. У страниц нет
  способа выдать доступ, в том числе самим себе.
- **Пароль** хранится как scrypt с солью в `application/passwords.py`, сравнение идет за
  постоянное время.
- **Сессия.** Браузер хранит случайный токен в cookie с флагами `HttpOnly` и `SameSite=Lax` и
  путем `/ui`, а по https еще и `Secure`. База хранит только sha256 токена, поэтому копия базы
  не дает войти.
- **CSRF.** Каждая форма несет токен своей сессии, а форма без него получает 403 и ничего не
  меняет. Так чужой сайт не отправит форму от имени оператора.
- **Подбор пароля.** После `MAX_FAILED_SIGN_INS` неверных паролей за `FAILURE_WINDOW` логин
  закрыт до конца окна. Неизвестный логин и неверный пароль получают один и тот же ответ за то
  же время, поскольку для неизвестного логина scrypt тоже считается.
- **Переход после входа** возможен только на страницу под `/ui/`, поэтому ссылка из письма не
  уведет оператора на чужой сайт.
- **Смена пароля и отключение** сразу закрывают все сессии логина.
- **Автором метки** записывается логин оператора с источником `ui`.
- **Карты «что видит модель» считаются по запросу.** Оценка фотографии не удлиняется ни на
  миллисекунду, карту рисует отдельный маршрут, когда оператор переключил вид на карточке.
  Энкодер для карт это вторая копия размером около 350 МБ, поэтому он грузится при первом
  запросе, а не при старте, и сервис, у которого карт не просят, за них не платит. Готовая
  карта лежит в `storage/` под именем из тройки «фотография, версия модели, вид», а второй
  просмотр сводится к чтению файла. Рисование идет по одной карте за раз, но под своей
  блокировкой, поэтому просмотр карты не задерживает оценку.
- **Нечитаемый кадр сервис бракует сам.** При непохожести от `review.unreadable_ood` в кадре нет
  кузова, и сценарий оценки тут же ставит метку «фотография непригодна» с источником `model`.
  Перевозка такой прогноз не считает, а XML API отвечает `photoUnusable="true"`. Карточка вместо
  числа показывает красную надпись, четыре измерения и одну кнопку «Фото читаемо». Кнопка
  снимает только вердикт модели и не трогает метку человека, после нее фотография возвращается в
  очередь и оценивается как обычная.

Ошибка на странице показывает сообщение и подсказку из каталога с тем же HTTP-статусом, что в
XML, и номер запроса для поиска в журнале. Непредвиденную ошибку журнал получает один раз, ее
пишет обработчик сервиса, а страница только показывает.

**Как страница узнает, что воркер запущен.** Воркер подключается к базе с именем приложения
`loadvision-worker`, а сервис ищет такое подключение в `pg_stat_activity` через
`infrastructure/db/activity.py`. Пока процесс воркера жив, его соединение остается в пуле между
опросами очереди, а с процессом пропадает. Поэтому не нужны ни таблица пульса, ни миграция, а
упавший воркер не выглядит живым.

Кнопки «Включить» и «Вернуть предыдущую модель» меняют активную версию в базе и сразу запускают
ее загрузку в фоне, а пока она грузится, отвечает прежняя. Шапка показывает версию, которая
отвечает сейчас, и если загрузка не удалась, страница «Модели» показывает причину.

Фотографии отдаются по адресу `/ui/photos/{sha256}` только вошедшему оператору. Хэш проверяется
по формату до обращения к хранилищу, поэтому адрес не может указать на другой файл.

## Настройки и секреты

Настройки сервиса лежат в `configs/app.yaml` и читаются в типизированную модель. Неизвестный
ключ или значение вне диапазона дают ошибку при старте, а не сюрприз в работающем сервисе. Там
же находятся лимиты фотографий, размер тела, папки хранилища, папка запусков и начальная версия
модели.

Секретов в файле нет. Строка подключения к базе берется из `DATABASE_URL`, а путь к самому файлу
настроек из `LOADVISION_CONFIG`.

## Наблюдаемость

- **Идентификатор запроса.** Клиентский `X-Request-ID` сохраняется, если подходит под формат,
  иначе выдается новый. Он есть в каждом ответе, в ошибке и в записи оценки.
- **События с постоянными именами** объявлены в `observability/events.py`. Пайплайн пишет
  `run.started`, `run.finished`, `stage.started`, `stage.finished` и `stage.failed` в
  `runs/<прогон>/run.jsonl`, а также `summary.json` со статусом каждого этапа. Сервис на каждый
  запрос пишет строку `request.finished` с идентификатором запроса, методом, путем, статусом и
  временем.
- **Логи в JSON.** Формат и уровень задаются в `configs/app.yaml`, секция `logging`. У строки
  лога те же ключи, что у записи прогона, а именно `ts`, `level`, `event` и `module`, поэтому
  один поиск по имени события находит ее и в логах, и в `runs/`. Тело запроса в лог не попадает,
  фотография в base64 заполнила бы его целиком.
- **Метрики моделей** лежат в `runs/`, это `oof/history.jsonl`, `oof/postprocess.jsonl` и
  `probes/encoders.jsonl`. Файлы дописываются, поэтому история замеров не теряется.

## Как все это проверяется

| Вид | Что проверяет |
|---|---|
| Быстрые тесты (`unit`, `api`, `ml`, `contract`) | сценарии на фейках, ответы по XSD, ML на синтетике, полторы тысячи за полминуты |
| Общие тесты порта | одно и то же поведение у фейка и у Postgres |
| Интеграционные | настоящий Postgres во временных базах, миграции, ограничения, гонки, сервис целиком |
| На данных (`data`) | проверки на реальном датасете |
| Мутационные | строка кода намеренно ломается, и проверяется, покраснеет ли тест |

Мутационные прогоны не формальность. Именно они показали слабые тесты, например проверку
идентификатора в верхнем регистре, которая не проверяла ничего, потому что идентификатор
состоял из цифр, и мертвый код, который после этого был удален.

Проверки собраны в один скрипт `scripts/check.sh`, он же стоит в хуке перед `git push`. Сборка
образа, `alembic upgrade head` и полный сценарий через HTTP проверялись на временной базе перед
слиянием.

## Что сознательно не делаем

| Не делаем | Вместо этого |
|---|---|
| Микросервисы | один процесс API и воркер |
| Celery, Redis, Kafka | очередь задач в Postgres на `SKIP LOCKED` |
| Kubernetes | Docker Compose, масштабирование репликами |
| ORM | SQLAlchemy Core с явными запросами |
| MLflow Registry | активная версия в Postgres |
| DVC | манифест, хэши файлов и `uv.lock` |
| SOAP | XML поверх REST с XSD |
