# Как устроен Loadvision

Версия от 17.09.2026. Документ описывает, что написано, и объясняет, почему именно так.
Незаконченное помечено явно: **в плане**. Как всё запускается - в `running.md`, ML-цепочка по
файлам - в `ml/pipeline.md`, журнал решений с датами - в `plan/notes.md`.

## Картина целиком

Сервис принимает фото кузова и номер перевозки в XML, оценивает загрузку 0-100%, сохраняет
оценку и отдаёт её по номеру перевозки. Оператор подтверждает настоящую загрузку или помечает
фото непригодным; эти метки идут в дообучение.

Код разложен по слоям, правило проверяет import-linter на каждом запуске проверок:

```
api | cli  →  infrastructure | ml  →  application  →  domain
```

| Слой | Что в нём |
|---|---|
| `domain` | перевозка, оценка, метка, версия модели и их правила |
| `application` | сценарии и порты (`Protocol`) |
| `infrastructure`, `ml` | Postgres, файлы, модель, пайплайн |
| `api`, `cli` | входные точки, сборка зависимостей |

Отдельно стоят общие модули: `errors.py` (каталог ошибок), `settings.py`, `imaging/`
(проверка и подготовка фото), `observability/`.

## Сущности

| Сущность | Где | Правила, которые она держит |
|---|---|---|
| `ShipmentId` | `domain/shipment.py` | формат номера: 1-64 латинских букв, цифр, `_`, `-`; та же строка повторена в XSD, тест сверяет обе копии |
| `Shipment` | там же | номер и время появления; перевозка создаётся первой оценкой |
| `LoadPercent` | `domain/assessment.py` | загрузка 0-100, конечное число; NaN и бесконечность отвергаются до сравнений |
| `Signals` | там же | неуверенность, непохожесть на обучающие, яркость, резкость; каждый сигнал либо неотрицательное число, либо «не считали» |
| `ReviewReason` | там же | причина ручной проверки: `low_confidence`, `unusual_scene`, `too_dark`, `blurry` |
| `Assessment` | там же | оценка фото в перевозке: загрузка, версия модели, время счёта, сигналы, причины, id запроса. `needs_review` не хранится, а выводится из причин |
| `ConfirmedLabel` | `domain/confirmed_label.py` | вердикт человека о фото: загрузка **или** «фото непригодно»; повтор заменяет вердикт, время первой метки сохраняется |
| `ModelVersion` | `domain/model_version.py` | версия пакета и её статус; разрешённые переходы статусов |
| `ImageRecord` | `application/ports.py` | описание фото: sha256, формат, размеры; байты лежат в хранилище |
| `PreparedImage` | `imaging/prepared_image.py` | декодированное фото: исходные байты, пиксели RGB и sha256, посчитанный тут же |

Два решения, которые экономят много сил дальше:

- **Загрузка хранится как есть, без округления.** Округление - это представление: XML пишет
  один знак после точки, база хранит точное число. Иначе повторные округления накапливаются.
- **Метка принадлежит фото, а не оценке.** Одно фото может попасть в несколько перевозок;
  подтверждённая загрузка от этого не меняется. Поэтому метка видна во всех оценках этого фото
  и в дообучение фото попадает один раз.

## Хранение: инварианты держит база

`infrastructure/db/tables.py` - эталон схемы, `migrations/versions/` - шаги, которыми схема
доводится до этого состояния. Интеграционный тест сравнивает мигрированную базу с таблицами из
кода: разойтись они не могут.

| Таблица | Ключевые ограничения |
|---|---|
| `images` | ключ - sha256; формат из списка, размеры положительные |
| `shipments` | ключ - номер, формат проверяется `CHECK` по тому же шаблону, что и в домене |
| `assessments` | `UNIQUE (shipment_id, image_sha256)`; загрузка в 0-100; причины проверки - только из известного списка |
| `confirmed_labels` | одна метка на фото; `CHECK (load_pct IS NULL) = unusable`; источник из списка; `updated_at >= created_at` |
| `model_versions` | частичный `UNIQUE`: активная версия ровно одна; время активации согласовано со статусом |
| `training_jobs` | частичный `UNIQUE`: одновременно выполняется одна задача обучения |

Списки допустимых значений в `CHECK` собираются из доменных перечислений прямо в коде таблиц,
поэтому новый статус или причина не могут появиться в домене и не появиться в базе.

Почему инварианты в базе, а не в коде: «одна активная модель» и «одно обучение за раз» должны
держаться при двух процессах и при гонке. Код может их только соблюдать, база - гарантировать.

**Числа с плавающей точкой.** Postgres ставит NaN выше любого числа, поэтому `CHECK (x >= 0)`
пропустил бы NaN. Диапазоны написаны так, чтобы NaN и бесконечность отсекались: `x >= 0 AND
x <= 100`, а для неотрицательных - `x >= 0 AND x < 'Infinity'`.

## Порты и репозитории: зачем абстракция

`application/ports.py` описывает, что сценарию нужно снаружи: репозитории перевозок, оценок,
фото, версий модели и меток, хранилище фото, предиктор и единицу работы. Это протоколы, а не
классы: реализация подставляется снаружи.

Абстракция стоит недорого: все пять репозиториев на Postgres - 320 строк SQLAlchemy Core,
фейковые в памяти - столько же. Взамен:

- **Тесты без базы.** Около 800 быстрых тестов проходят за 4 секунды на фейках в памяти.
  Интеграционные тесты на настоящем Postgres - отдельный набор, 122 теста.
- **Одни и те же тесты для обеих реализаций.** `tests/port_contracts/` - это набор тестов
  поведения, который гоняется и на фейке, и на Postgres. Фейк не может «разойтись» с базой
  незаметно: если реализация в памяти умеет то, чего не умеет Postgres, красный тест это
  покажет. Фейк даже повторяет частичный уникальный индекс: попытка активировать вторую версию
  падает и в памяти.
- **Замена без правки сценариев.** Сборка приложения с настоящей базой не потребовала ни одной
  правки в `application/`.

Почему SQLAlchemy Core, а не ORM: нам нужны ровно те запросы, которые мы написали. ORM добавила
бы ленивую загрузку, кеш сессии и неожиданные `SELECT` в цикле - на хакатоне это отладка на
ровном месте. Core даёт типобезопасную сборку SQL и явные запросы.

**Единица работы** (`PostgresUnitOfWork`) - это одна транзакция на один сценарий:

```python
with self.uow_factory() as uow:  # взяли соединение из пула, началась транзакция
    uow.assessments.add(assessment)  # изменения видны только внутри
    uow.commit()  # сохранили
# выход без commit или с исключением - всё откатилось, соединение вернулось в пул
```

Две ловушки, на которые мы уже наступили и закрыли тестами:

- **Повтор фото не ловится исключением.** Нарушение уникальности обрывает всю транзакцию в
  Postgres, а порт обещает, что после повтора единицей работы можно пользоваться дальше.
  Поэтому вставка оценки идёт через `INSERT ... ON CONFLICT DO NOTHING RETURNING id`: если
  ничего не вернулось, оценка уже есть.
- **`rowcount` у SQLAlchemy Core на psycopg равен −1** для `insert()`, хотя у самого psycopg он
  верный. Поэтому факт вставки проверяется через `RETURNING`, а не по числу строк.

## Идемпотентность: что именно блокирует дубли

Дубли блокируются не полем в запросе, а содержимым фото.

1. Фото узнаётся по `sha256` своих байтов. Клиенту не нужен ключ идемпотентности: одно и то же
   фото - это одно и то же фото.
2. В базе стоит `UNIQUE (shipment_id, image_sha256)`. Второй такой пары не будет физически.
3. Сценарий сначала читает: если оценка этой пары уже есть, он возвращает её и **не запускает
   модель**. В ответе `reused="true"` и статус 200 вместо 201.
4. Если то же фото пришло в другой перевозке, создаётся новая оценка, но прогноз берётся из
   старой по паре «sha256, версия модели»: модель второй раз не считает.
5. Если параллельный запрос успел закоммитить первым, наш вставит ничего, прочитает его оценку
   и вернёт её как повтор. Это проверено интеграционным тестом с двумя потоками: второй поток
   ждёт коммита первого и получает ожидаемый отказ, а не случайную ошибку.

Дополнительная выгода: фото в хранилище лежит по своему хэшу, поэтому повторная присылка не
создаёт второй файл, а запись фото на диск идёт через временный файл с переименованием -
читатель никогда не увидит недописанное фото.

Порядок записи выбран намеренно: **сначала файл, потом база**. Если упадёт база, останется
лишний файл; при обратном порядке осталась бы запись без фото.

## XML-контракт

Одна схема `api/xsd/loadvision-v1.xsd` описывает все сообщения и отдаётся клиенту по
`GET /api/v1/schema.xsd`. Форматы, которые живут ещё и в коде (номер перевозки, версия модели,
коды ошибок, причины проверки, форматы файлов, id запроса), повторены в схеме намеренно, а тест
сверяет обе копии - разъехаться они не могут.

Что делает разбор запроса:

- парсер создаётся заново на каждый документ, без DTD, без внешних сущностей и без сети, поэтому
  классическая атака XXE не проходит; `DOCTYPE` отклоняется отдельно;
- документ проверяется по XSD до того, как код что-то из него читает;
- ошибка XSD переводится в код: только про `ShipmentId` - `INVALID_SHIPMENT_ID`, только про
  `Image` - `INVALID_ENCODING`, иначе `INVALID_XML`. В подробности для лога попадают только
  имена элементов: сообщение libxml2 может процитировать значение, а значение `Image` - это всё
  фото;
- base64 декодируется строго ещё раз: libxml2 проверяет его нестрого и пропускает префикс
  `data:image/jpeg;base64,`. Пробелы и переносы строк разрешены - так base64 переносят Java,
  openssl и почтовые кодировщики;
- размер тела проверяется до чтения: если заявленный `Content-Length` больше лимита, ответ 413
  приходит, не прочитав ни байта; потоковое тело читается в память до лимита и обрывается.

В ответах есть два правила, о которых стоит помнить:

- `Review` пишется, только когда есть причины. Пока политики ручной проверки нет, пустой набор
  означает «не проверяли», а `needed="false"` утверждало бы больше, чем сервис знает.
- Метка фото приходит либо загрузкой, либо пустым элементом `Unusable`. Схема запрещает оба
  сразу и запрещает ни одного, поэтому «брак с загрузкой 70» невозможен на уровне контракта.

## Каталог ошибок

Один каталог `errors.py` на API, пайплайн и логи. У кода есть HTTP-статус, сообщение и подсказка
на русском. Тексты не содержат чисел лимитов и форматов: лимиты живут в конфиге, формат номера -
в домене и XSD, иначе копии разойдутся.

| Код | HTTP | Когда |
|---|---|---|
| `INVALID_CONTENT_TYPE` | 415 | тело не `application/xml` |
| `INVALID_XML` | 400 | не разбирается, не проходит схему, есть DOCTYPE |
| `INVALID_SHIPMENT_ID` | 400 | номер перевозки не того формата |
| `INVALID_ENCODING` | 400 | фото не в строгом base64 |
| `PAYLOAD_TOO_LARGE` | 413 | тело или фото больше лимита |
| `UNSUPPORTED_FORMAT` | 415 | файл не JPEG, PNG или WebP (HEIC узнаётся и называется явно) |
| `CORRUPTED_IMAGE` | 422 | не декодируется, обрезан, слишком мал или слишком много пикселей |
| `SHIPMENT_NOT_FOUND` | 404 | нет такой перевозки |
| `ASSESSMENT_NOT_FOUND` | 404 | нет такой оценки или id не каноничный |
| `ROUTE_NOT_FOUND` | 404 | нет такого адреса |
| `METHOD_NOT_ALLOWED` | 405 | не тот метод; ответ несёт заголовок `Allow` |
| `TRAINING_ALREADY_RUNNING` | 409 | дообучение уже идёт (**в плане**, воркера ещё нет) |
| `MODEL_VERSION_STATUS_CONFLICT` | 409 | запрещённый переход статуса версии |
| `MODEL_NOT_READY` | 503 | модель ещё не загрузилась |
| `MODEL_INFERENCE_FAILED` | 500 | модель упала или вернула значение вне 0-100 |
| `STAGE_CHECK_FAILED` | - | постусловие этапа пайплайна; клиенту не показывается |
| `MODEL_PACKAGE_INVALID` | - | пакет модели не прошёл проверку |
| `INTERNAL_ERROR` | 500 | всё остальное, без подробностей наружу |

Правила, которые делают ошибки безопасными: подробности (`detail`) идут только в лог, в ответе
их нет; код без HTTP-статуса никогда не уходит клиенту как есть, он превращается в
`INTERNAL_ERROR`; в каждом ответе есть `requestId`, по которому запрос ищется в логах.

## Фото: одна дверь для всех

`imaging/validator.py` - единственный путь от байтов к пикселям, и для сервиса, и для обучения.
Порядок проверок выбран так, чтобы дорогие шаги шли после дешёвых: пустой файл, размер,
сигнатура формата по содержимому файла, затем размеры из заголовка (до распаковки пикселей) и
только потом полное декодирование.

Полное декодирование обязательно: `verify()` у Pillow пропускает обрезанные файлы. Поворот по
EXIF и перевод в RGB делаются ровно так же, как это делает обучение, поэтому модель в сервисе
видит то же изображение, что видела при обучении. Это общий контракт: правку в этом файле
согласовывают оба владельца.

Пиксели после декодирования помечаются только для чтения. Члены ансамбля читают одно и то же
изображение, и если бы один из них нормализовал его на месте, следующий получил бы испорченный
вход - теперь такая попытка падает сразу.

## Модель - это сущность со статусами

Модель поставляется **пакетом**: папка с `manifest.json` и файлами весов. Манифест описывает
версию, членов ансамбля (энкодер, рантайм, файл головы, вес, препроцессинг), цепочку
постобработки, коммит кода, хэш датасета и sha256 каждого файла. При загрузке хэши проверяются:
подменённый или недокачанный файл до сервиса не доедет.

Версии живут в таблице `model_versions` со статусами и разрешёнными переходами:

```
candidate ──→ active ──→ retired ──→ active   (откат: возвращаем ту, что уже работала)
    └────→ rejected                            (тупик: отвергнутую не активируют)
```

Переходы проверяет домен, единственность активной версии - база. Время активации и статус
согласованы ещё одним `CHECK`.

Версиями управляют три команды: `model register` кладёт пакет в папку моделей и записывает
версию кандидатом, `model activate` включает её и отправляет прежнюю в отставку, `model
rollback` возвращает ту, что работала до текущей. Регистрация и активация разделены намеренно:
пакет может существовать и не отвечать на запросы.

Что сервис делает при старте (`application/load_served_model.py`):

1. спрашивает базу, какая версия активна;
2. если активной нет, берёт начальную версию из настроек;
3. грузит пакет и проверяет, что манифест объявляет ту же версию;
4. только после успешной загрузки записывает версию в базу как активную.

Поэтому сломанный пакет не становится активной версией, а каждая сохранённая оценка ссылается на
существующую запись версии. Пока модель грузится, сервис уже отвечает: чтение работает, оценка
даёт 503. Загрузка идёт в фоновом потоке, прогнозы выполняются по одному - torch-модель не
рассчитана на одновременные вызовы, а один прогноз получает все ядра.

Запрос, который взял модель, досчитывает на ней, даже если в этот момент активировали другую:
в оценке записана версия, которая её действительно сделала.

## Дообучение и защита от деградации

Замысел: метки оператора → новая модель-кандидат → проверка → активация или отказ. Что из этого
уже есть и что в плане:

| Часть | Состояние |
|---|---|
| Метки с браком фото, отбор пригодных для обучения | сделано |
| Пайплайн обучения как набор этапов с постусловиями | сделано |
| Честный OOF на фиксированных фолдах | сделано |
| Пакет модели с манифестом и хэшами | сделано |
| Версии со статусами, единственная активная, откат | сделано в домене и базе |
| Очередь задач и воркер | сделано |
| Промоушен-гейт (сравнение кандидата с активной) | сделано, вызывается воркером |
| Постановка задачи через API | **в плане**, сейчас команда `jobs start` |

Что уже защищает от деградации:

- **Фолды никогда не меняются.** `configs/splits/folds.json` лежит в git, а команда сборки
  отказывается перезаписать файл, если хоть одно фото поменяло бы фолд. Иначе сравнение версий
  между собой ничего не значило бы.
- **Оценка модели - только вне обучения.** Каждое фото предсказывается моделью, которая его не
  видела, и вместе с ним не видела других фото того же кузова: фолды держат сцену целиком.
- **Прогноз старой модели уже сохранён.** В `assessments` записана загрузка и версия модели.
  Когда появятся новые подтверждённые фото, кандидата можно сравнить с действующей моделью на
  тех же фото, ничего не пересчитывая.
- **Постобработка подгоняется вне фолда.** Порог или кривая никогда не видят фото, на которых их
  судят, иначе выигрыш был бы нарисованным.
- **Разброс по фолдам считается и показывается.** Улучшение меньше разброса не считается
  улучшением.
- **Пакет проверяется при загрузке.** Хэши файлов, поддерживаемый рантайм, и пробный прогон на
  пустом фото: несовместимая голова падает при загрузке, а не на первом запросе клиента.

**Как устроена очередь.** Задача - это строка в `training_jobs` со статусами
`queued → running → succeeded | failed`. Воркер работает тремя короткими шагами, между которыми
не держит транзакцию: берёт задачу, обучает, записывает исход.

- Задачу берут запросом `SELECT ... FOR UPDATE SKIP LOCKED`: второй воркер не ждёт занятую
  строку, а проходит мимо неё.
- Пока одна задача выполняется, новая не берётся, и частичный уникальный индекс держит то же
  правило в базе.
- Обучение идёт вне транзакции: оно длится минуты, и соединение с базой не должно его ждать.
- Если воркер падает на задаче, она записывается неудачной до того, как исключение полетит
  наверх: иначе она осталась бы «выполняющейся» навсегда и закрыла бы очередь.
- Отвергнутый гейтом кандидат - это успешная задача: обучение отработало, а гейт сделал свою
  работу. Версия регистрируется, но не включается.
- Пакет кандидата попадает в папку моделей и регистрируется до активации, поэтому включается
  только то, что сервис действительно может загрузить.

## Настройки и секреты

Настройки сервиса - `configs/app.yaml`, читаются в типизированную модель: неизвестный ключ или
значение вне диапазона - ошибка при старте, а не сюрприз в проде. Там же лимиты фото, размер
тела, папки хранилища, папка запусков и начальная версия модели.

Секретов в файле нет: строка подключения к базе берётся из `DATABASE_URL`, а путь к самому файлу
настроек - из `LOADVISION_CONFIG`.

## Наблюдаемость

- **Идентификатор запроса.** Клиентский `X-Request-ID` сохраняется, если подходит под формат,
  иначе выдаётся новый. Он есть в каждом ответе, в ошибке и в записи оценки.
- **События с постоянными именами** - `observability/events.py`. Пайплайн пишет `run.started`,
  `run.finished`, `stage.started`, `stage.finished`, `stage.failed` в `runs/<прогон>/run.jsonl`
  плюс `summary.json` со статусом каждого этапа. Имена `request.finished`, `model.activated` и
  `gate.rejected` объявлены заранее, но ещё не пишутся.
- **Структурные логи в JSON** - **в плане**, сейчас логи идут стандартным `logging`.
- **Метрики моделей** - в `runs/`: `oof/history.jsonl`, `oof/postprocess.jsonl`,
  `probes/encoders.jsonl`. Файлы дописываются, поэтому история замеров не теряется.

## Как всё это проверяется

| Вид | Что проверяет |
|---|---|
| Быстрые тесты (`unit`, `api`, `ml`, `contract`) | сценарии на фейках, ответы по XSD, ML на синтетике; около 800 штук за 4 секунды |
| Общие тесты порта | одно и то же поведение у фейка и у Postgres |
| Интеграционные | настоящий Postgres во временных базах: миграции, ограничения, гонки, сервис целиком |
| На данных (`data`) | проверки на реальном датасете |
| Мутационные | мы ломаем строку кода и смотрим, покраснеет ли тест |

Мутационные прогоны - не формальность: именно они показали слабые тесты (проверка id в верхнем
регистре не проверяла ничего, потому что id состоял из цифр) и мёртвый код, который потом был
удалён.

Проверки собраны в один скрипт `scripts/check.sh`: он же стоит в хуке перед `git push` и в CI.
Сборка образа, `alembic upgrade head` и полный сценарий через HTTP проверялись на временной базе
перед слиянием.

## Что сознательно не делаем

| Не делаем | Вместо этого |
|---|---|
| Микросервисы | один процесс API и воркер |
| Celery, Redis, Kafka | очередь задач в Postgres на `SKIP LOCKED` |
| Kubernetes | Docker Compose, масштаб репликами |
| ORM | SQLAlchemy Core с явными запросами |
| MLflow Registry | активная версия в Postgres |
| DVC | манифест, хэши файлов и `uv.lock` |
| SOAP | XML поверх REST с XSD |

## Чего ещё нет

- постановка задачи через API: пока только команда `jobs start`, в XSD нет сообщений о задачах;
- отдельный образ воркера: он запускается из репозитория, потому что образу api не нужен torch;
- образ API собран без torch, поэтому в контейнере поднимается только пакет на numpy. Пакет на
  энкодерах предиктор понимает, но для контейнера нужен образ с группой `ml` (задача 10.1);
- сигналы яркости и резкости и политика ручной проверки;
- структурные логи и опрос активной версии на ходу;
- UI оператора;
- оценка веса груза (бонус организаторов) и выбор энкодеров под приемлемой лицензией - открытые
  вопросы К7 и К8 в `plan/open-questions.md`.
