# Документация Loadvision

Задача: по фото грузового отсека и номеру перевозки вернуть загрузку 0-100%, сохранить её, отдать по XML API и уметь дообучаться на подтверждённых метках. Метрика - MAE в процентных пунктах.

## Порядок ML-цепочки

Один запуск - шесть этапов, каждый со своими постусловиями:

```
build_manifest       фото и метки -> manifest.csv, проверки целостности
extract_embeddings   замороженные энкодеры -> векторы в кэш по sha256
train_folds          голова на 4 фолдах -> предсказание 5-го -> oof.csv
evaluate             oof.csv -> metrics.json, cases.json, worst_oof.csv
predict_test         голова на всех метках -> submission.csv
build_package        головы, кривые, веса, манифест -> package/
```

Запуск: `uv run loadvision train configs/experiments/<имя>.json --device mps`.
Результат - папка `runs/run_<время>_<хвост>/` с `summary.json`, `run.jsonl` и артефактами.

Подробности каждого шага - в `ml/pipeline.md`.

Перед этим обязательно добавить хэш весов энкодера в ключ кэша эмбеддингов, иначе старые векторы молча смешаются с новыми.
2. **PDF-презентация** - ML-слайды.
3. **Should:** срезы по типам груза, стресс-тест устойчивости, оценка веса как описанное расширение без числа в ответе.

**Проверено и отклонено 17.09** (подробности в `ml/experiments.md`): сплайновая калибровка PCHIP, многомасштабная пирамида, TTA отражением. Ни одна не дала выигрыша за свою цену.

## Открытые вопросы к владельцу B

- Порог неуверенности для флага `low_confidence` описать в манифесте нечем: у `ood` есть `threshold`, у неуверенности нет. Предложение - `review: {uncertainty: float}` рядом с `ood`.
- `blurry` сервис **не выставляет**: замер показал, что в наших данных размытие ошибку не предсказывает, а сильно размытый кадр и так далеко от обучающих (0.47 против порога 0.23). `too_dark` с 20.09 выставляется, но не как предсказатель ошибки, а как отказ от кадра, на котором груза не видно: порог 20 из 255 при самом тёмном фото датасета 21.6. В XSD причины остаются.
- Этап `build_package` кладёт веса копией из кэша Hugging Face - это заготовка под его `model pull`.

## Команды

```
uv sync                                   поставить всё
scripts/check.sh                          ruff, pyright, import-linter, быстрые тесты
uv run pytest -m data                     проверки на реальном датасете, нужен data/
uv run loadvision data folds              собрать configs/splits/folds.json
uv run loadvision data folds --check      только проверить файл
uv run loadvision features probe          kNN-зонд по реестру энкодеров, без обучения
uv run loadvision train configs/experiments/<имя>.json   весь пайплайн
uv run loadvision eval heads              перебор энкодеров и голов по OOF
uv run loadvision eval postprocess        перебор цепочек постобработки
uv run loadvision eval errors             отчёт по ошибкам с графиками в runs/eda/
uv run loadvision model build-baseline    пакет baseline в storage/models/
```

Команды `eval` и `features` - исследовательские: они перебирают варианты и пишут историю в
`runs/`. `train` - производственный: он считает одну конфигурацию из конфига и оставляет папку
прогона.

## Правила ведения документации

- решение зафиксировано - строка в `plan/notes.md` с датой и причиной
- проверенный факт про библиотеку или лицензию - в `plan/facts.md`, со ссылкой
- замер - строка в `ml/experiments.md` и, если он повторяемый, запись в `runs/`
- вопрос без ответа - в `plan/open-questions.md` с владельцем
- спека контракта меняется вместе с кодом, в одном коммите
