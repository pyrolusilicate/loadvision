## Как пользоваться

- В начале сессии читать этот файл и `CLAUDE.md`. Задачи с ID — в `decomposition.md`, проверенные цифры и источники — в `facts.md`, детали API, БД и пайплайна из плана A — в `plan-a-spec.md`, открытые вопросы — в `open-questions.md`.
- Лицензии, лимиты платформ и версии пакетов меняются. Прежде чем опираться на них в новом решении, перепроверить по источнику и обновить дату в `facts.md`.
- Новое решение записывать сюда сразу: дата, что решили, почему.

### Архитектура и стек

- База — план A «Loadvision» v1 от 15.09. План от Gemini отброшен. (решено 15.09)
- Слои: `api | cli` → `infrastructure | ml` → `application` → `domain`. Три forbidden-контракта: домен без фреймворков; application без веба, БД, XML и ML; общие модули (`errors`, `settings`, `observability`, `imaging`) не импортируют слои проекта и ML-рантаймы. (решено 16.09)
- БД: PostgreSQL, SQLAlchemy 2 **sync** и psycopg 3. Async не нужен: модель всё равно считается в отдельном потоке. (решено 15.09)
- SQLite не берём: в базу одновременно пишут API и CLI или воркер дообучения, а SQLite допускает одного пишущего; нет `FOR UPDATE SKIP LOCKED` для очереди; файл базы между контейнерами ненадёжен; типизация слабая. (решено B 16.09)
- SQLAlchemy **Core**, не ORM: таблицы и запросы; репозиторий явно собирает неизменяемые доменные dataclass из строк. ORM требует изменяемых объектов с отслеживанием изменений и ленивой загрузкой. Транзакция — на `UnitOfWork`. Alembic — миграции с откатом и проверкой расхождений по метаданным таблиц. (решено B 16.09)
- XML: lxml (проверка XSD на libxml2, явные настройки безопасного парсера); типы для pyright — `types-lxml` в dev: без них pyright не видит `lxml.etree`. (решено B 16.09)
- API (решено B 17.09):
  - XML разбирается и собирается вручную на lxml: безопасный парсер → проверка по XSD → чтение полей; pydantic-xml не берём — сообщений мало, форму уже держит XSD, вторая модель формы разошлась бы с ней. Ответы в тестах сверяются с XSD.
  - Сервис стартует и без модели: пакет грузится в фоне, пока не загружен или загрузка упала — `/health` и `POST /assessments` отвечают 503 `MODEL_NOT_READY`, причина в логе; чтение сохранённых оценок работает.
  - base64 фото: пробелы и переносы строк пропускаются (Java, openssl и почтовые кодировщики переносят по 76 символов), остальное декодируется строго — чужие символы и префикс `data:` дают `INVALID_ENCODING`.
  - Настройки: модель pydantic читает `configs/app.yaml` через PyYAML; из окружения — только секреты (`DATABASE_URL`) и путь к конфигу. pydantic-settings не берём.
  - Модель в сервисе: вызовы предиктора по одному через блокировку — в каждый момент считается одно фото, torch отдаёт ему все ядра. Сценарий получает предиктор через порт `LoadPredictor`, так что батчер (3.8) заменит блокировку без правок API; брать ли его — по нагрузочному замеру. Массовая загрузка своих фото — последовательным скриптом, прогноз по папке без базы — этапом `predict` A.
  - Пакет: `configs/app.yaml` → `model.version`, папка пакета `storage.models_dir / version` (та же раскладка у `model pull` и у активации из базы, 3.9); `model.device`, `model.threads`.
  - Новые коды каталога: `ROUTE_NOT_FOUND` (404) и `METHOD_NOT_ALLOWED` (405), чтобы на неизвестный адрес и метод FastAPI отвечал XML, а не своим JSON.
  - Порт подтверждённых меток (`ports.py`, общий контракт) — отдельной веткой после ядра API: его читает обучение A.
- Рантайм и поставка модели (решено A и B 17.09, В15–В17):
  - Сначала torch, ONNX — оптимизация по замеру. Рантайм — класс на члена ансамбля; `runtime` в манифесте у члена, `device` (cpu или cuda) и число потоков — в настройках сервиса. CUDA не «одна строка»: нужен другой образ (torch с CUDA или `onnxruntime-gpu`, NVIDIA Container Toolkit), код не меняется. Одинаковые чекпоинт и препроцессинг у разных членов (pooled и grid) — один прогон энкодера.
  - Интернет не нужен на старте: образ для сдачи несёт веса отдельным слоем (до кода) и текст лицензии DINOv3; для разработки пакет монтируется томом `storage/models`. Сборка многоэтапная (uv собирает `.venv` без dev, во второй этап — только `.venv` и код), torch из CPU-индекса PyTorch, `.dockerignore` для `data/`, `runs/`, `.venv`; размер образа измерить и записать в README.
  - Ансамбль заранее не режем: 4 члена = 2 прогона энкодера; облегчённый пакет для сервиса — только если нагрузочный замер покажет, что медленно.
- UI: Jinja2 + htmx 2.x локальным файлом, без сборки фронтенда. UI вызывает сценарии application напрямую, не через XML API. (решено 15.09)
- Фото передаются только в base64 внутри XML. (план A)
- Быстрое дообучение — только на замороженных энкодерах. Фолды существующих строк не меняются. Источник правды для метрик — `runs/`. (`CLAUDE.md`, 16.09)
- Зависимости: `default-groups = "all"`; `uv add` — только после согласования с A; pyright ставится как `pyright[nodejs]`. (решено 16.09)

### ML

- Энкодеры: DINOv3-B и DINOv2-B считаем параллельно до дня 3. (решено 15.09)
- На день 2 добавить PE-Spatial-B и SigLIP 2-B. Правило выбора на день 3: берём лучший энкодер под Apache-2.0 или MIT, если DINOv3 не лучше него значимо. «Значимо» — средняя парная разница абсолютных ошибок на одних и тех же OOF-фото больше двух её стандартных ошибок. (предложено 15.09)
- Дисбаланс меток не выравниваем по умолчанию: тест распределён как train. Голова по 21 бину с медианой; веса групп 1/√n и мягкое выравнивание — только эксперимент при значимом выигрыше. (предложено 16.09)
- Аугментации (предложено 16.09):
  - можно: горизонтальное отражение (и для TTA), яркость, контраст, гамма, затемнение с шумом, размытие, JPEG и пересжатие, поворот до ±5°, отдаление, обрезка сверху и по бокам до ~10%, имитация масок анонимизации и рамок скриншотов;
  - проверить: лёгкая перспектива;
  - нельзя: обрезка снизу (там пол у двери: 80 становится 100), вертикальное отражение, крупный cutout, Mixup, CutMix, центральный кроп в квадрат;
  - аугментированные варианты нужны и в кэше эмбеддингов (id аугментации входит в ключ), копии остаются в фолде исходного фото;
  - тест инвариантности: каждое преобразование применяется к OOF-фото, систематический сдвиг прогноза значит, что преобразование меняет правильный ответ.
- kNN-признак: соседей в OOF искать только в обучающих фолдах. (предложено 16.09)
- Вход модели вертикальный, фиксированного размера, без центрального кропа в квадрат. Проверено 16.09: 709 из 716 фото train вертикальные, но пропорции разные — 1440×1920 (3:4) только у 298 фото, есть 1080×1920 (9:16) и почти квадратные вроде 606×700, всего 188 разных размеров. Значит, ресайз с паддингом, а не растяжение, и низ кадра не обрезать. (предложено 15.09, уточнено 16.09)

## Контракты v1 (подход подтверждён B 16.09; с A ещё не согласован)

**Порядок реализации:** `errors.py` → `domain/` → `imaging.PreparedImage` и `application/ports.py` → фейки для тестов → XSD v1 и примеры XML → манифест пакета (вместе с A) → имена событий, протокол Stage, первая миграция.

**Когда A и B работают независимо:**

- **A** может писать этапы и пакет v0 после манифеста v0 и протокола Stage.

### `errors.py`

- `ErrorCode` — строковый enum (StrEnum). Каталог: код → `ErrorSpec(http_status: int | None, message: str, hint: str)`. Одно исключение `LoadvisionError(code)`, в API один обработчик на все коды.
- Коды по-английски, сообщения и подсказки по-русски.
- `http_status = None` у ошибок пайплайна, например `NONFINITE_EMBEDDINGS`.
- Коды: из плана A плюс `MODEL_INFERENCE_FAILED` (500) и `MODEL_VERSION_STATUS_CONFLICT` (409). Полный список со статусами и текстами — только в `src/loadvision/errors.py`, здесь он не дублируется.

- `MODEL_INFERENCE_FAILED`: исключение в предикторе, NaN или прогноз вне [0, 100]. Клиенту — сообщение и подсказка «повторите запрос, повтор безопасен». Детали (тип исключения, трейсбек, request_id) — только в лог.
- `InvalidShipmentIdError` удалён: `ShipmentId` бросает `LoadvisionError(ErrorCode.INVALID_SHIPMENT_ID)`. Отдельные классы исключений — только там, где их нужно ловить отдельно.
- Конкретные тексты подсказок дописываем по мере появления ошибок.
- Реализовано 16.09 в `feat/contracts-v1`:
  - `ERROR_CATALOG` — `MappingProxyType`: изменить его во время работы нельзя;
  - значения кодов заданы явно и равны именам: `StrEnum` с `auto()` дал бы строчные;
  - `LoadvisionError(code, detail=None)`: `detail` только для логов, без байтов фото, base64 и секретов; `str(error)` — `"КОД"` или `"КОД: detail"`; свойство `spec` отдаёт запись каталога;
  - свой `__reduce__`: стандартная сериализация исключения повторно вызывает конструктор с текстом сообщения вместо кода и падает, а ошибка должна переживать передачу из воркера и пула процессов;
  - в текстах нет цифр лимитов и формата номера: лимиты живут в `configs/app.yaml`, формат — в домене и XSD; подсказки отсылают к документации API и `GET /api/v1/schema.xsd`;
  - тесты проверяют полноту каталога, значения кодов, диапазон HTTP-статусов, непустые тексты, неизменяемость каталога, `str`, `spec` и сериализацию; каждая из шести мутаций валит ровно свои тесты.
- Ловушка мутационных проверок (16.09): Python сверяет кэш байткода по времени изменения файла с точностью до секунды и по размеру. Если поломка не меняет размер файла, а восстановление идёт в ту же секунду, тесты гоняют старый байткод. Перед каждым прогоном чистить `__pycache__` и ставить `PYTHONDONTWRITEBYTECODE=1`.

### `domain/`

- `LoadPercent`: Python `float` (это всегда 64-битный double), проверка `math.isfinite` и 0 ≤ x ≤ 100. Хранится **сырое** значение.
- Округление до одного знака — только в слое API при сборке XML, одной общей функцией. В Python `round` и `format` округляют половины к чётному на двоичном представлении, так что «школьного» округления от них не ждать.
- Клип в [0, 100] — ответственность ML: модель отвечает за свой диапазон, домен только проверяет.
- `ShipmentId` (готов): шаблон без якорей `"[A-Za-z0-9_-]{1,64}"` — XSD якорит шаблон сам, и та же строка идёт в XSD. Проверка через `fullmatch`: `re.match` с `^…$` пропускает `\n` в конце.
- `Assessment`: id, shipment_id, image_sha256, load_pct, uncertainty (может отсутствовать), ood_score (может отсутствовать), needs_review, review_reasons, model_version, processing_ms, request_id, created_at.
- Поля доверия заводим сразу, в XSD они необязательные; на демо пустыми не показываем. В ТЗ они не требуются: это Should, польза для пользователей и устойчивость.
- `model_version` в оценке нужен для разбора ошибок (оценка → версия → манифест → коммит, хэш данных, конфиг), а не для отката.
- id и время: сценарий получает функции `now()` и `new_id()`. Домен сам не вызывает `datetime.now()` и `uuid4()`.
- `ModelVersion`: статусы candidate, active, rejected, retired; переходы проверяет домен.
- Реализовано 16.09 в `feat/contracts-v1`:
  - **Какую ошибку бросает домен:** `LoadvisionError` с кодом — когда смысл для клиента всегда один (неверный `ShipmentId`, недопустимая смена статуса версии); `ValueError` — когда смысл зависит от вызывающего (`LoadPercent`, сигналы, sha256, `ModelVersionId`, время без часового пояса), и тогда код ставит вызывающий слой.
  - `domain/timestamps.py`: `ensure_aware` — единственная проверка часового пояса для всех сущностей.
  - `LoadPercent`: проверка `not isfinite or < 0 or > 100`. Без `isfinite` NaN прошёл бы: любое сравнение с ним ложно.

  - Метрики версии (MAE, доля ≤ 10 п.п.) в домен не входят: их источник — манифест пакета, база хранит копию для запросов.

### Сервис на Postgres (0.3, 5.5, 5.6, 6.2, 6.4; B 17.09)

ON CONFLICT DO NOTHING RETURNING id`, а не перехват нарушения уникальности: ошибка оборвала бы всю транзакцию, а порт обещает, что единица работы остаётся рабочей. ### Модели, приоритеты и вес (решено B 17.09)

- Финальная модель — на весах не от Meta: Meta в РФ признана экстремистской, а заказчик — Почта России. От Meta не только DINOv3, но и DINOv2, PE-Spatial и PE-Core, ConvNeXt — весь текущий лучший ансамбль (DINOv3 + PE-Spatial, OOF 7.124). Пока идут эксперименты, модели Meta можно использовать для сравнения. Кандидаты из таблицы лицензий: SigLIP 2 (Google, Apache-2.0; по kNN-зонду в одной группе с DINOv3 и PE-Spatial) и EVA-02 B/14 (BAAI, MIT). Решение — по OOF на тех же фолдах (К7). PyTorch вышел из Meta, но с 2022 им управляет PyTorch Foundation под Linux Foundation: граница — веса, выпущенные Meta.
- Порядок работ до сдачи: 1) обязательная часть целиком — `GET` перевозки, репозитории Postgres, api в compose, метки, CLI дообучения, gate, активация и откат, финальный пакет на моделях не от Meta; 2) оценка веса — бонус от организаторов, берём обязательно; 3) UI и сервис, доступный извне; 4) интеграции-демонстрации: папка-приёмник вместо FTP (`inbox/` → XML с результатом рядом), бот в MAX через наш API (сначала проверить API ботов MAX). Интеграции вне обязательного объёма и в README идут в «Ограничения», на защите — как готовность через порты.
- Оценка веса без разметки веса (план, К8): вес ≈ занятый объём × насыпная плотность вида груза. Вид груза (палеты, тележки-контейнеры, пластиковые контейнеры, мешки, посылки навалом) — без обучения по текстовым описаниям в SigLIP 2 (текстовая часть — через open_clip или transformers, в timm только картиночная), проверка — A размечает глазами 50–100 фото по виду груза. Объём — доля занятой площади пола × площадь пола кузова × высота штабеля; габариты кузова — необязательное поле запроса или таблица по типу машины, высота — типовая для вида груза. Плотности — таблица в конфиге как допущения, ответ — диапазон «от–до». Калибровка — подтверждённым весом тем же циклом дообучения.

## 17.09: что на самом деле означает метка

Разбор худших OOF-ошибок вместе с пользователем (он смотрел фото глазами) опроверг рабочую гипотезу.

**Было:** метка примерно равна доле длины пола от передней стенки до фронта груза.

**Стало:** метка - это **доля занятой площади пола**. Проверено на `img_1826a8294b2bb22595a9`: пустой кузов, три коробки с мешком у правой стенки примерно в середине глубины, метка **2**, модель говорит **41**. Если бы считалась глубина, эксперт поставил бы около 50.

Второй тип промаха оттуда же: груз стоит почти у края, но неплотно - модель даёт 70-80, эксперт ставит 100.

Следствия:

- Общий вектор энкодера (один на всю картинку) описывает сцену, а не покрытие пола. Отсюда систематическое завышение на редком грузе.
- Прямое лечение - брать не один вектор, а пространственную сетку патчей: доля «грузовых» клеток и есть занятая площадь. Добавлены варианты реестра с `pooling="grid"`.
- Пользователь отмечает, что разметка шумная. Значит есть неустранимый пол ошибки; оценить его отдельно.
- Оба типа промаха (16 + 8 фото) дают 11.1% суммарной ошибки.

**Метрика платформы - это MAE, меньше лучше** (В14 закрыт): версия с OOF 7.58 дала 8.90 против 11.42 у версии с OOF 10.71. Лимит отправок 20 в день (В5 закрыт).

Разрыв между OOF и платформой вырос с 0.71 до 1.32. Часть выигрыша от калибровки на тесте не воспроизвелась - калибровочная кривая подогнана под распределение train. Следить за этим разрывом дальше.

**Нужна правка манифеста пакета (общий контракт, решение вдвоём):** в `postprocess` добавить необязательное поле для калибровочной кривой, например `calibration: {file, sha256}`, и зафиксировать порядок применения: кривая -> `round_to` -> `snap_100` -> обрезка в 0-100. Кривая хранится двумя массивами точек в `.npz`, без pickle.

## 17.09: во что мы целимся (решение пользователя)

Ставка проекта - **не самый низкий MAE, а самый надёжный сервис**. Обоснование: предобученный энкодер с линейной головой даёт похожий результат у любой команды, которая его возьмёт, поэтому средняя метрика нас не отличает. Отличает то, знаем ли мы свои слабые места численно и сообщает ли сервис о неуверенности.

Из этого следуют четыре обязательства, они же материал защиты:

1. Метрики считаются **по сценариям**, а не только в среднем. Каталог сценариев - `docs/ml/user-cases.md`, он живой.
2. Каждый прогон оставляет **отчёт с примерами фотографий** по каждому сценарию, чтобы на защите говорить конкретикой, а не «мы тестировали».
3. Сервис отдаёт **сигналы доверия** и флаг ручной проверки с порогами, подобранными на OOF.
4. **Стресс-тест** с таблицей деградации: затемнение, JPEG, размытие, поворот.

Правило оценки изменений: улучшение среднего при ухудшении сценария - повод разобраться, а не праздновать.

Сценарии, найденные пользователем на фотографиях 17.09: почти пустой кузов с парой коробок в глубине (модель 40, правда 2) и забитый неплотно кузов (модель 80-90, эксперт 100). Оба попали в каталог.

## 17.09: лицензии едут вместе с весами (хвост К7 закрыт, A)

Если текста для названной лицензии нет, сборка падает: выпустить веса без условий хуже, чем уронить прогон. На это есть тест.

Текст Apache-2.0 взят канонический, из установленного timm, с возвращённой на место заглушкой `[yyyy] [name of copyright owner]` вместо копирайта самого timm - настоящих правообладателей называет NOTICE.

**Записан отдельный результат: перебор стоит секунды.** Полный прогон семи вариантов калибровки на трёх разбиениях - 21 честная оценка ансамбля со всеми фолдами - занимает 2.25 секунды, потому что замороженный энкодер и кэш по SHA-256 фотографии отделяют дорогую часть от дешёвой. Без кэша это было бы около двух часов. Это причина, по которой три гипотезы внешнего ресёрча удалось отклонить за вечер.
