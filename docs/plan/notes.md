## Как пользоваться

- В начале сессии читать этот файл и `CLAUDE.md`. Задачи с ID — в `decomposition.md`, проверенные цифры и источники — в `facts.md`, детали API, БД и пайплайна из плана A — в `plan-a-spec.md`, открытые вопросы — в `open-questions.md`.
- Лицензии, лимиты платформ и версии пакетов меняются. Прежде чем опираться на них в новом решении, перепроверить по источнику и обновить дату в `facts.md`.
- Новое решение записывать сюда сразу: дата, что решили, почему.

### `errors.py`

- `ErrorCode` — строковый enum (StrEnum). Каталог: код → `ErrorSpec(http_status: int | None, message: str, hint: str)`. Одно исключение `LoadvisionError(code)`, в API один обработчик на все коды.
- Коды по-английски, сообщения и подсказки по-русски.
- `http_status = None` у ошибок пайплайна, например `NONFINITE_EMBEDDINGS`.
- Коды: из плана A плюс `MODEL_INFERENCE_FAILED` (500) и `MODEL_VERSION_STATUS_CONFLICT` (409). Полный список со статусами и текстами — только в `src/loadvision/errors.py`, здесь он не дублируется.

- `MODEL_INFERENCE_FAILED`: исключение в предикторе, NaN или прогноз вне [0, 100]. Клиенту — сообщение и подсказка «повторите запрос, повтор безопасен». Детали (тип исключения, трейсбек, request_id) — только в лог.
- `InvalidShipmentIdError` удалён: `ShipmentId` бросает `LoadvisionError(ErrorCode.INVALID_SHIPMENT_ID)`. Отдельные классы исключений — только там, где их нужно ловить отдельно.
- Конкретные тексты подсказок дописываем по мере появления ошибок.
- Реализовано 16.09 в `feat/contracts-v1`:
  - `ERROR_CATALOG` — `MappingProxyType`: изменить его во время работы нельзя;
  - значения кодов заданы явно и равны именам: `StrEnum` с `auto()` дал бы строчные;
  - `LoadvisionError(code, detail=None)`: `detail` только для логов, без байтов фото, base64 и секретов; `str(error)` — `"КОД"` или `"КОД: detail"`; свойство `spec` отдаёт запись каталога;
  - свой `__reduce__`: стандартная сериализация исключения повторно вызывает конструктор с текстом сообщения вместо кода и падает, а ошибка должна переживать передачу из воркера и пула процессов;
  - в текстах нет цифр лимитов и формата номера: лимиты живут в `configs/app.yaml`, формат — в домене и XSD; подсказки отсылают к документации API и `GET /api/v1/schema.xsd`;
  - тесты проверяют полноту каталога, значения кодов, диапазон HTTP-статусов, непустые тексты, неизменяемость каталога, `str`, `spec` и сериализацию; каждая из шести мутаций валит ровно свои тесты.
- Ловушка мутационных проверок (16.09): Python сверяет кэш байткода по времени изменения файла с точностью до секунды и по размеру. Если поломка не меняет размер файла, а восстановление идёт в ту же секунду, тесты гоняют старый байткод. Перед каждым прогоном чистить `__pycache__` и ставить `PYTHONDONTWRITEBYTECODE=1`.

### `domain/`

- `LoadPercent`: Python `float` (это всегда 64-битный double), проверка `math.isfinite` и 0 ≤ x ≤ 100. Хранится **сырое** значение.
- Округление до одного знака — только в слое API при сборке XML, одной общей функцией. В Python `round` и `format` округляют половины к чётному на двоичном представлении, так что «школьного» округления от них не ждать.
- Клип в [0, 100] — ответственность ML: модель отвечает за свой диапазон, домен только проверяет.
- `ShipmentId` (готов): шаблон без якорей `"[A-Za-z0-9_-]{1,64}"` — XSD якорит шаблон сам, и та же строка идёт в XSD. Проверка через `fullmatch`: `re.match` с `^…$` пропускает `\n` в конце.
- `Assessment`: id, shipment_id, image_sha256, load_pct, uncertainty (может отсутствовать), ood_score (может отсутствовать), needs_review, review_reasons, model_version, processing_ms, request_id, created_at.
- Поля доверия заводим сразу, в XSD они необязательные; на демо пустыми не показываем. В ТЗ они не требуются: это Should, польза для пользователей и устойчивость.
- `model_version` в оценке нужен для разбора ошибок (оценка → версия → манифест → коммит, хэш данных, конфиг), а не для отката.
- id и время: сценарий получает функции `now()` и `new_id()`. Домен сам не вызывает `datetime.now()` и `uuid4()`.
- `ModelVersion`: статусы candidate, active, rejected, retired; переходы проверяет домен.
- Реализовано 16.09 в `feat/contracts-v1`:
  - **Какую ошибку бросает домен:** `LoadvisionError` с кодом — когда смысл для клиента всегда один (неверный `ShipmentId`, недопустимая смена статуса версии); `ValueError` — когда смысл зависит от вызывающего (`LoadPercent`, сигналы, sha256, `ModelVersionId`, время без часового пояса), и тогда код ставит вызывающий слой.
  - `domain/timestamps.py`: `ensure_aware` — единственная проверка часового пояса для всех сущностей.
  - `LoadPercent`: проверка `not isfinite or < 0 or > 100`. Без `isfinite` NaN прошёл бы: любое сравнение с ним ложно.
  - `Signals` (uncertainty, ood_score, brightness, sharpness): все необязательные; присутствующие — конечные и неотрицательные. Проверка идёт по `fields()`, так что новое поле проверится автоматически.
  - `ReviewReason`: low_confidence, unusual_scene, too_dark, blurry.
  - `Assessment`: только именованные аргументы (`kw_only`), чтобы не перепутать соседние числа и строки; `needs_review` — свойство, вычисляемое из `review_reasons`, а не поле; sha256 — 64 строчных hex-символа; `processing_ms` ≥ 0.
  - `ModelVersionId`: `MODEL_VERSION_PATTERN = "[A-Za-z0-9][A-Za-z0-9._-]{0,63}"`. Первым символом не может быть точка: версия — это сегмент URL и имя папки в хранилище моделей.
  - Переходы `ModelVersion`: candidate → active или rejected; active → retired; retired → active (откат); rejected — конечный статус. Таблица переходов — единственное место правила: докстринги и подсказка ошибки её не пересказывают.
  - `activated_at` задан тогда и только тогда, когда версия хоть раз была активной (active, retired); `retire` сохраняет время активации.
  - «Одна активная версия» — инвариант базы, а не домена: сценарий активации снимает текущую активную и активирует новую в одной транзакции. Повторная активация уже активной версии — решение сценария (идемпотентность), домен считает её конфликтом.
  - Метрики версии (MAE, доля ≤ 10 п.п.) в домен не входят: их источник — манифест пакета, база хранит копию для запросов.
  - 15 мутаций, каждая валит ровно свои тесты.

### `imaging.PreparedImage`

- Живёт в `imaging/`, а не в `application/ports.py`. Иначе получится цикл импортов: контракт запрещает `imaging` импортировать `application`, а `application` использует `imaging`.
- Поля: `sha256`, `media_type`, `pixels: NDArray[np.uint8]` формы (H, W, 3), RGB, EXIF уже применён, исходный размер; `raw: bytes` для `ImageStorage`. Ширина и высота берутся из `shape`, отдельно не хранятся.
- Это декодированное фото, а не вход модели. Вход модели (ресайз с паддингом до вертикального входа фиксированного размера, нормализация, форма (3, H, W)) делает `imaging/preprocessing.py` по параметрам из манифеста.
- Реализовано 16.09 в `imaging/prepared_image.py`; решения про вычисляемый `sha256`, пиксели только для чтения и сравнение по идентичности подтверждены B 16.09:
  - `MediaType`: image/jpeg, image/png, image/webp — формат определяется по содержимому файла;
  - `PreparedImage(raw, media_type, pixels)`: `sha256` не передаётся, а вычисляется из `raw`, поэтому не может с ним разойтись; `height` и `width` берутся из `shape`;
  - пиксели доступны только для чтения: участник ансамбля, нормализующий изображение на месте, испортил бы вход следующему;
  - `eq=False` — сравнение по идентичности объекта: иначе `==` сравнивал бы массивы numpy и падал;
  - нарушение структуры (пустые байты, не uint8, не (H, W, 3), нулевой размер) — `ValueError`: `PreparedImage` создаёт наш декодер, а коды ошибок для клиента (`CORRUPTED_IMAGE` и другие) ставит валидатор.
- numpy 2.5.3 добавлен в основные зависимости 16.09 — показать A на ревью.

### `application/ports.py`

- `LoadPredictor` (Protocol):
  - свойство `version: ModelVersionId` — доменный тип, а не строка;
  - `predict(images: Sequence[PreparedImage]) -> list[Prediction]`: та же длина и тот же порядок;
  - метода для одного фото нет;
  - при сбое модели падает весь батч: сценарий отдаёт `MODEL_INFERENCE_FAILED`, батчер — ошибку каждому запросу в батче.
- `Prediction` — frozen dataclass: `load_pct: LoadPercent`, `uncertainty` и `ood_score` типа `float | None` со значением None по умолчанию. Здесь сигналы не проверяются: их правила живут в `Signals`, куда сценарий их переносит.
- `Clock`, `IdFactory`, `UnitOfWorkFactory` — типы функций, которые сценарии получают снаружи.
- Репозитории синхронные и работают внутри `UnitOfWork`:
  - `ShipmentRepository`: `get`; `add` оставляет существующую перевозку как есть, так что гонка двух первых запросов безопасна;
  - `AssessmentRepository`: `add` при дубле (перевозка, sha256) бросает `AssessmentAlreadyExistsError`, и `UnitOfWork` после этого остаётся рабочим (в Postgres это вставка внутри SAVEPOINT); `get`; `find_by_shipment_and_image`; `find_by_image_and_model` — переиспользование прогноза для того же фото в другой перевозке; `list_by_shipment` — новые первыми;
  - `ImageRepository`: `add` идемпотентно по sha256, `get` — метаданные для таблицы `images` (ширина и высота нужны в XML-ответе);
  - `ModelVersionRepository`: `get`, `get_active`, `list_all` (новые первыми), `add`, `update`.
- `ImageRecord` — метаданные фото; строится через `ImageRecord.from_prepared`, чтобы совпадать с фото.
- `ImageStorage`: `save` идемпотентно, `load`; работает вне транзакции БД. Порядок: сначала файл, потом коммит записи — неудачный коммит оставит лишь неиспользуемый файл.
- `UnitOfWork`: контекстный менеджер, репозитории как свойства, `commit`; выход без `commit` или с исключением — откат. «Создать перевозку + сохранить оценку» — атомарно. Этого порта не было в плане A, добавлено 16.09.
- Базового класса в `ml` нет: протокол, фейк в `tests/fakes/` и настоящий `ml/inference/predictor.py`, который загружает пакет. Заглушку предиктора в рабочем коде через настройки не делаем.
- Пакет v0 — Ridge из `baseline/`: обёртка — A, загрузчик — B.
- Проверено 16.09: 10 мутаций `PreparedImage` и `ImageRecord`, каждая валит ровно свои тесты. Протоколы поведения не имеют — их проверят фейки и общие тесты портов.

### XSD v1

- Пространство имён `urn:loadvision:api:v1`, тело `application/xml; charset=utf-8`, схема по `GET /api/v1/schema.xsd`. (план A)
- `LoadPct` — `xs:decimal`: NaN и бесконечности в нём непредставимы.
- Шаблон `ShipmentId` — та же строка, что `SHIPMENT_ID_PATTERN`; тест сверяет их, когда появится XSD.
- Элементы review и signals необязательные.
- `DeclaredLoadPct` — процент из нормативного отчёта (Should, предложено, с A не согласовано).

### Первая миграция

- `load_pct double precision` и `CHECK (load_pct BETWEEN 0 AND 100)`. Проверить тестом, что NaN не проходит CHECK: в Postgres NaN считается больше любого числа, ожидаем отказ.
