# Loadvision: декомпозиция проекта

Версия 1 от 15.09.2026. Дополняет план «Loadvision» v1 от 15.09.2026. Если пункты противоречат, действует раздел «Что изменилось относительно плана v1».

## Как разбирать

Разбираем параллельно, потом сводим правки в этот файл и переносим в Miro.

- **A (ML, напарник) со своим Claude** проверяет части 1 и 2, этапы и gate из части 4, экспорт из части 3 (3.3, 3.4), задачи 9.3–9.5 и общие части 0 и 10.
- **B (платформа: backend + MLOps) с Claude** проверяет части 3–10 и часть 0.

Что проверить в каждой задаче:

1. Успеваем ли в указанный день с учётом зависимостей.
2. Хватает ли задач, чтобы закрыть требование условия, и нет ли лишних.
3. Можно ли проверить критерий «Готово, когда» без споров.
4. Нет ли противоречий с планом v1, с разделом «Что изменилось» и с приоритетом.

Формат ответа — одна строка на правку, чтобы правки двух сторон сводились механически:

```text
2.8 ИЗМЕНИТЬ: день 3 → 4, зависит ещё от 2.9
НОВАЯ после 5.6: удаление метки, если оператор ошибся (B, день 4, S)
УДАЛИТЬ 5.14: X-API-Key не нужен для демо
ВОПРОС 4.9: какое N новых меток брать в gate
ОК: 1.1–1.10
```

Перенос в Miro: часть = фрейм, задача = стикер с ID, цвет = владелец (A, B, AB), колонки = дни 1–7, тег = приоритет, стрелки = зависимости.

## Контекст

Сервис по фото грузового отсека и номеру перевозки возвращает загрузку 0–100%. Метка — экспертная оценка **занятой площади пола**. Прежняя приписка «примерно равна доле длины пола от передней стенки до фронта груза» опровергнута 17.09: на редком грузе это разные числа, см. `notes.md`. Основная метрика — MAE в процентных пунктах; на своей валидации дополнительно считаем долю ошибок не больше 10 п.п. Данные: 716 train, 307 test (153 public, 154 private). Baseline: MAE 19,1 и 32,9% ошибок не больше 10 п.п.

Сдаём: XML API (оценка фото, привязка к перевозке, чтение по номеру, понятные ошибки), воспроизводимое дообучение на подтверждённых метках, README по пунктам условия, `submission.csv`, видео MP4 до 5 минут и 200 МБ, PDF до 15 слайдов и 20 МБ. Все материалы описывают одну версию решения.

## Обозначения

- **Кто:** A — ML (напарник); B — платформа: backend + MLOps; AB — вместе.
- **Пр. (приоритет):** M — Must, без этого не сдаём; S — Should, заметно добавляет баллов; C — Could, если останется время.
- **День:** номер дня из таблицы сроков; «2–3» — задача растянута на два дня.
- **OOF** — прогноз для фото от модели, которая это фото не видела при обучении.
- **Gate** — PromotionGate, проверка «новая версия модели не хуже активной».

## Роли

- **A:** данные, сплиты, эмбеддинги, головы, LoRA, ансамбль, kNN-признак, сигналы доверия, evaluate и `worst_oof`, экспорт в ONNX и паритет с torch, критерии gate и пороги `review_policy`.
- **B:** формат пакета модели, загрузчик, `model pull` и публикация весов; рантаймы ONNX и torch в сервисе, батчер, `ActiveModel`; каркас пайплайна (протокол Stage, runner, кэш, `runs/`, structlog); воркер, очередь, активация и откат; API, БД, UI; CI, образы, compose, обвязка бенчмарка и нагрузки.

Каркас пайплайна пишет B, этапы в `ml/pipeline/stages/` пишет A.
