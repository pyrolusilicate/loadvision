# Сессия на L4: от запуска машины до `/vm_stop`

Машина арендованная, часы идут всё время, пока она включена, даже если GPU простаивает. Поэтому всё, что можно, делается до запуска машины, а на ней - только готовые прогоны. Факты о машине и лимите - в `../plan/facts.md`, раздел 9.

Всё управление - одним скриптом с твоего компьютера: `scripts/gpu/remote.sh <шаг>`. Вывод каждого шага пишется ещё и в `runs/gpu/<время>_<шаг>.txt`.

## Перед сессией

- Выключить VPN: с ним порт 22 машины недоступен.
- Проверить, что команда запускается: `uv run python -m loadvision.cli.commands.finetune --help`. Она не зависит от остальных команд CLI, поэтому поломка в чужой команде сессию не блокирует.
- Отредактировать `scripts/gpu/plan.sh` - это список того, что посчитать в эту сессию, по порядку ценности.

## Шаги

1. В боте `@codenrock_yc_bot`: `/vm_start`, затем `/status`. Адрес из `/status` записать одной строкой в `runs/gpu/host`, например `yc-user@<ip>`. После каждого запуска машины адрес может смениться.
2. `bash scripts/gpu/remote.sh upload` - код, данные (354 МБ) и эталон для сравнения: предсказания текущей поставки на тех же фото.
3. `bash scripts/gpu/remote.sh setup` - **только в первую сессию**: uv, Python 3.12, зависимости и torch под CUDA 12. Зафиксированный в lock torch собран под CUDA 13 и на драйвере 535 машины GPU не увидит. В конце скрипт доказывает, что GPU реально обучает. Окружение остаётся на диске между остановками.
4. `bash scripts/gpu/remote.sh quick` - необязательно: один фолд, одна эпоха самой тяжёлой модели (728, кроп, глубина), чтобы убедиться, что весь путь работает и влезает в память. Заодно ставит transformers.
5. `bash scripts/gpu/remote.sh start` - запускает `plan.sh` на машине в `tmux` и сразу возвращает терминал. После этого можно закрыть ноутбук и включить VPN: расчёт идёт на машине.
6. `bash scripts/gpu/remote.sh status` - сколько сделано, последние строки логов, загрузка GPU. Сколько угодно раз.
7. `bash scripts/gpu/remote.sh fetch` - забрать прогоны **без весов** в `runs/finetune/` и логи в `runs/gpu/logs/`. Веса лежат на диске машины; `fetch-weights` забирает и их, когда нужен пакет модели.
8. **`/vm_stop` в боте** и `/status` до `STOPPED`. Закрытый терминал машину не останавливает.

## Что лежит в папке прогона

Прогон на пяти фолдах:

- `oof.csv` - предсказание каждого обучающего фото моделью, которая его не видела, в формате пайплайна
- `metrics.json` - `mae_raw` до калибровки, `mae` после, флаг `calibrated`, разбивка по фолдам и диапазонам
- `settings.json` - настройки, файл фолдов, коммит
- `folds/fold_<n>/encoder.safetensors` и `head.npz` - веса каждой из пяти моделей фолдов (ViT-B около 350 МБ на фолд, ViT-L около 1.2 ГБ); `--no-weights` их не сохраняет
- `test_folds.csv` - предсказание теста каждой моделью фолда, `test_raw.csv` - их среднее: готовый ответ прогона для отправки и для ансамбля, без отдельного обучения на всех фото

Прогон на всех фото (`--full`) вместо этого:

- `encoder.safetensors` и `head.npz` - модель в тех двух файлах, которые несёт пакет модели для члена ансамбля
- `test_raw.csv` - сырые предсказания теста с полной точностью, из них собирается ансамбль
- `submission.csv` - ответ для платформы

После каждого фолда `oof.csv` сохраняется сразу, так что остановка машины посреди прогона не теряет готовые фолды.

## Как читать результат

Последние строки лога прогона на пяти фолдах:

```
photos 716   MAE before calibration X   after Y   within10 Z
reference  on 716 shared photos: before calibration ...   after ...
this run   on 716 shared photos: before calibration ...   after ...
```

Эталон по умолчанию - поставленная модель, DINOv2 B e15 (5.72). Сравнивать `after` этого прогона с `after` эталона. Правило то же, что у всех наших решений: разница меньше 0.35 на одном разбиении улучшением не считается, перспективное подтверждается на `folds_seed1.json` и `folds_seed2.json`.

## После сессии: ансамбль, у себя, без GPU

Из готовых прогонов на пяти фолдах, за секунды:

```bash
# какой состав лучше: перебирает все комбинации прогонов
uv run python -m loadvision.cli.commands.blend runs/finetune/<прогон_1> runs/finetune/<прогон_2> ... --search

# выбранный состав: каждый член по отдельности, ансамбль и парная разница с лучшим членом
uv run python -m loadvision.cli.commands.blend <прогоны> --reference runs/run_20260917_154153_6bbb20/oof.csv

# отправка ансамбля: среднее по тесту всех моделей фолдов всех членов
uv run python -m loadvision.cli.commands.blend <прогоны> --submit
```

Ансамбль усредняет сырые предсказания членов и калибрует среднее один раз. Прогоны должны быть на одних и тех же фолдах. Лучший состав из перебора выбран на тех же фото, на которых измерен, поэтому его число чуть приукрашено - перед поставкой подтверждать на `folds_seed1.json` и `folds_seed2.json`.

## Пакет модели для сервиса

Из прогона `--full` и прогона на пяти фолдах с теми же настройками, у себя, без GPU:

```bash
uv run loadvision model build-finetuned runs/finetune/<прогон_full> --oof-run runs/finetune/<прогон_oof> --version v2 --device mps
```

Пакет пишется в `<прогон_full>/package/`: дообученный энкодер, голова, калибровка и метрики из прогона на фолдах, эталон для необычных сцен из эмбеддингов самого дообученного энкодера, лицензия и NOTICE с пометкой, что веса изменены. Сервис грузит веса энкодера из пакета начиная с `feat/operator-ui`; без этой ветки он молча возьмёт предобученный энкодер с дообученной головой. `model fetch` дообученные веса не скачает: их нет на Hugging Face, пакет передаётся целиком.
