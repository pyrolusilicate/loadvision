# Loadvision

Сервис оценки загрузки грузового отсека по фотографии: прогноз 0-100%, привязка к номеру перевозки, XML API и дообучение на подтверждённой разметке.

**Качество:** MAE **5.76** на честной кросс-валидации по 716 фото, **4.82** на публичном рейтинге платформы. Baseline организаторов - 19.1. Доля прогнозов с ошибкой не больше 10 п.п. - 87%.

**Скорость:** 2.0 с на фото, CPU ноутбука MacBook Air M4, без видеокарты; сервис целиком, от XML до ответа, - 2.2 с. Требование организаторов - «не больше нескольких секунд».

**Лицензии:** все веса под Apache-2.0 - дообученный нами DINOv2 и сеть глубины Depth Anything V2 Small; их тексты и NOTICE едут внутри пакета модели.

Подробный отчёт по всем замерам, включая отброшенные гипотезы: [`docs/ml/experiments.md`](docs/ml/experiments.md). Устройство ML-цепочки файл за файлом: [`docs/ml/pipeline.md`](docs/ml/pipeline.md).

## Требования

- [uv](https://docs.astral.sh/uv/) 0.12+
- Python 3.12 (uv установит сам)
- [just](https://github.com/casey/just) для коротких команд, необязательно
- Docker для локального Postgres

## Команды

После `uv sync` доступна команда `loadvision`:

```bash
uv run loadvision model build-baseline                       # пакет модели в storage/models/
uv run loadvision train configs/experiments/<имя>.json       # весь пайплайн обучения
uv run loadvision predict submission                         # прогноз пакетом модели
uv run loadvision data folds --check                         # проверить configs/splits/folds.json
uv run loadvision eval heads                                 # сравнение энкодеров и голов по OOF
uv run loadvision eval errors                                # отчёт об ошибках в runs/eda/
uv run python scripts/ood_scale.py data/probe                # где фото лежат на шкале модели
uv run python scripts/ood_line.py --help                     # подобрать черту допустимости фото
```

Обучение и сравнение моделей требуют `data/` и группы зависимостей `ml`. Сервису хватает пакета
модели в `storage/models/`.

## Сервис

Веса поставляемой модели не лежат в репозитории: пакет весит два гигабайта. Он опубликован на
Hugging Face под Apache-2.0 и ставится тремя командами.

```bash
cp .env.example .env                       # пароль базы: в POSTGRES_PASSWORD и в DATABASE_URL
just up                                    # Postgres, миграции и API на http://localhost:8000

uv run --with huggingface_hub hf download Roman3427/loadvision-truck-load-v4 --local-dir storage/handoff/v4
uv run --env-file .env loadvision model register storage/handoff/v4
uv run --env-file .env loadvision model activate v4

uv run --env-file .env loadvision operators add <логин>   # вход на страницы
```

Проверка: `curl -s localhost:8000/health` отвечает `modelVersion="v4"`. Без этих трёх команд
сервис поднимется на `baseline-v0` - это решение организаторов с MAE 19.1, а не наше.

Пакет можно и не скачивать: `uv run loadvision model build-baseline` соберёт baseline, и
сервис заработает на нём. Так удобно смотреть API, но числа будут чужие.

## Скорость под нагрузкой

Замер сервиса целиком, а не одной модели: в него входят разбор XML, декодирование фото, модель,
база и ответ. Команда `just loadtest 4 24` шлёт фото параллельными клиентами и пишет отчёт в
`runs/loadtest/`. У каждого запроса своё фото: повтор сервис отдаёт из сохранённого и модель не
зовёт.

Ноутбук MacBook Air M4 (4 производительных ядра и 6 экономичных), сервис без Docker, модель v4
на CPU, видеокарта не используется:

| Клиентов | Задержка p50 | p95 | Фото в секунду |
|---|---|---|---|
| 1 | 2.17 с | 2.59 с | 0.46 |
| 4 | 7.04 с | 7.41 с | 0.56 |
| 4, повтор того же фото | **25 мс** | 89 мс | **96** |

Для сравнения, только модель, без сервиса вокруг (`loadvision bench`): v4 - 1.98 с, одна модель
вместо пяти (пакет v3) - 0.61 с. То есть на обвязку сервиса уходит около 180 мс из 2.17 с,
остальное считает модель.

Что из этого следует. Пропускная способность не растёт с числом клиентов: модель считает по
одному фото за раз, и очередь перед ней превращается в задержку. Это сознательное решение -
один прогноз занимает все ядра, и параллельные прогнозы отнимали бы их друг у друга. Чтобы
поднять пропускную способность, сервис запускают в несколько процессов, по копии модели на
каждый. Повторное фото отвечается почти в сто раз быстрее: прогноз берётся из базы.

Число потоков почти ничего не меняет: 4 потока - 2.02 с, 6 - 1.95 с, 8 - 1.91 с. В Docker на
том же ноутбуке ответы в несколько раз медленнее: сборка torch под linux/arm64 в виртуальной
машине не использует ускорители процессора Apple. Поэтому сервис на macOS запускается
командой `just serve`, без контейнера.

## Как устроена модель

Фотографий 716 - для обучения сети с нуля мало, поэтому берётся готовый энкодер DINOv2 ViT-B/14 и **дообучается** на наших фото. Именно дообучается: тот же энкодер в замороженном виде, как переводчик под линейной головой, давал 10.45, а дообученный - 5.72. Замороженный путь в сервисе остался, но для другого - быстрого дообучения на подтверждённых метках.

Поставляемая модель (пакет `v4`) - это:

| Часть | Что делает |
|---|---|
| пять дообученных DINOv2 ViT-B/14 | по одной модели на каждый фолд, ответы усредняются в равных долях |
| Depth Anything V2 Small | карта относительной глубины, свёрнутая в сетку 16x12 |
| линейная голова | 768 чисел энкодера плюс 192 числа глубины на входе, загрузка на выходе |
| калибровка и округление | медиана по 16 бинам, отдельно для двух пропорций кадра, затем округление до 5 |

Голов в сервисе две, и манифест говорит какая: поле `head_kind` со значениями `linear`
(ридж-голова в `.npz`, все пакеты до 21.09) и `bins` (веса в safetensors). Поле аддитивное -
его отсутствие означает `linear`, поэтому старые пакеты грузятся без изменений.

**Почему глубина.** Метка - доля занятого объёма, а по одному кадру не видно, как далеко вглубь уходит груз. Сеть глубины отвечает на это прямо. Честно про выигрыш: на нашей кросс-валидации она не дала **ничего** (+0.05 при разбросе 0.26), на платформе пара прогонов сдвинулась с 5.10 до 4.90. Обе величины внутри шума замера, поэтому мы не утверждаем, что глубина помогает - мы утверждаем, что она не мешает, а отправляли мы лучший из замеренных вариантов. Стоит она около 170 мс на фото.

**Почему пять моделей, а не одна.** Одна модель на тех же настройках даёт на платформе 4.90 против 4.80 у пятёрки и считается втрое быстрее. Разница в баллах неразличима - шум платформы на 153 фото около 0.57. Пятёрка выбрана не из-за 0.1, а потому что среднее пяти моделей устойчивее к одной неудачной: разброс их ответов мы к тому же отдаём клиенту как сигнал неуверенности.

**Почему калибровка.** Голова, обученная на квадрат ошибки, отвечает ближе к середине, когда не уверена: на метке 100 сырой прогноз в среднем 94.6. Калибровка по медиане в бинах выпрямляет это. Кривых две - датасет распадается на две популяции по пропорциям кадра, и одна общая кривая помогает большей и портит меньшую.

Что проверяли и отбросили, включая отрицательные замеры, - в [`docs/ml/experiments.md`](docs/ml/experiments.md).

## Обучение и прогноз

Датасет кладётся в `data/train` и `data/test` (в git не попадает).

**Сданная модель.** Две команды: дообучение по фолдам, затем сборка пакета из полученных пяти моделей. Нужна видеокарта - на CPU дообучение считается часами.

```bash
# пять фолдов DINOv2 с картой глубины; оставляет прогон в runs/finetune/
uv run loadvision finetune configs/finetune/dinov2_b14_depth.json --device cuda

# пакет из пяти моделей этого прогона, с его же калибровкой и метриками
uv run loadvision model build-finetuned runs/finetune/<прогон> --version v4 --device cuda
```

Пакет кладётся в папку прогона; `loadvision model register <папка>` переносит его в `storage/models/`, `model activate v4` включает в сервисе. `submission.csv` для платформы прогон пишет сам.

**Замороженный путь** остался для быстрого дообучения на подтверждённых метках: энкодер не трогается, учится только голова поверх кэша эмбеддингов, и это считается минутами на CPU. Им же пользуется воркер сервиса.

```bash
uv run loadvision train configs/experiments/ens4_apache_by_aspect.json --device mps
```

Одна команда проходит шесть этапов, каждый со своими постусловиями, и оставляет папку прогона `runs/run_<время>_<хвост>/`:

```
manifest.csv     таблица данных с проверками целостности
oof.csv          прогноз на каждое обучающее фото от модели, которая его не видела
metrics.json     метрики прогона
cases.json       таблица по сценариям с примерами фотографий
worst_oof.csv    40 худших фото, чтобы посмотреть глазами
submission.csv   ответ для платформы, 307 строк
package/         то, что загружает сервис: головы, кривые, веса, манифест с хэшами
summary.json     статус каждого этапа, счётчики, метрики, артефакты
run.jsonl        события прогона
```

`--device` принимает `cpu`, `mps` или `cuda`. Без GPU прогон идёт дольше только на этапе эмбеддингов; всё остальное считается на CPU за секунды.

Прогноз в сервисе делается загрузкой `package/` - отдельной команды для этого не нужно, постусловие этапа `build_package` уже загружает пакет тем же классом, которым его загружает сервис, и предсказывает им.

Другие полезные команды:

```bash
uv run loadvision data folds                     # собрать configs/splits/folds.json
uv run loadvision data folds --check             # только проверить существующий файл
uv run loadvision features probe                 # kNN-зонд по реестру энкодеров, без обучения
uv run loadvision eval heads                     # перебор энкодеров и голов по OOF
uv run loadvision eval postprocess               # перебор цепочек постобработки
uv run loadvision eval errors                    # отчёт по ошибкам с графиками в runs/eda/
uv run loadvision model build-baseline           # пакет baseline в storage/models/
uv run pytest -m data                            # проверки на реальном датасете
```

## Дообучение на подтверждённых метках

Когда оператор подтверждает загрузку на фотографии, метка попадает в базу. Дообучение забирает такие метки и строит новую версию модели:

1. **Датасет.** Базовый датасет плюс подтверждённые фото. Базовые фото линкуются, а не копируются, и папка `data/` не изменяется: прогон обязан быть повторяемым из тех же входов. Фото, которое уже есть в базе, меняет метку на месте; новое становится отдельной сценой.
2. **Фолды.** Новые фото получают фолд, **старые строки не двигаются никогда**. Без этого сравнение версий было бы сравнением разных разбиений. Правило записано в [`docs/plan/folds-json.md`](docs/plan/folds-json.md).
3. **Пайплайн.** Те же шесть этапов, что и в исследовании, - не отдельный скрипт.
4. **Gate.** Кандидат сравнивается с активной версией **только на фотографиях, которые обе видели**, и только вне своих фолдов. Порог: не меньше 20 новых меток, и кандидат не хуже активной больше чем на 0.3 - это измеренный шум разбиения.

Отказ gate - это **успешный** прогон: обучение отработало, а решение не пускать приняли осознанно. Провалом считается только прогон, не собравший пакет. Причину решения видно в таблице задач: «кандидат хуже активной на 716 общих фото: +0.512 при допуске +0.30». Допуск 0.30 - не подобранное число, а измеренный шум разбиения: та же модель на трёх разных фолдах даёт MAE с размахом 0.22-0.34 ([experiments.md](docs/ml/experiments.md)).

**Кандидат строится в той же семье, что и активная модель.** Иначе gate сравнивал бы архитектуры, а не метки: раньше воркер учил четыре замороженных энкодера с ридж-головами против пяти дообученных в сервисе, и отказ означал «замороженное хуже дообученного» - факт, известный заранее и к дообучению отношения не имеющий.

Теперь берутся **те же энкодеры активного пакета**, замороженными, и заново обучаются только головы - на датасете, куда добавлены подтверждённые метки. Энкодеры не трогаются, поэтому прогон стоит одного прохода по фотографиям, появившимся с прошлого раза: кэш эмбеддингов и кэш карт глубины ключуются хэшем фото и переживают перезапуск. На 716 фото прогон занимает 16 секунд при тёплом кэше против 22 минут на холодном.

Сеть глубины берётся из самого пакета, а не с Hugging Face: пакет везёт её копию именно затем, чтобы ничего не скачивать, и на машине организаторов выхода в хаб нет. Прогон проверен с `HF_HUB_OFFLINE=1` - числа те же.

Две тонкости, от которых зависит, значит ли что-нибудь число, которое читает gate:

- **Голов обучается по две на члена.** Та, что едет в пакете, видит все фото - энкодер заморожен, утекать нечему. Та, по которой считается `metrics/oof.csv`, видит только фолды, на которых дообучался её собственный энкодер, поэтому фото, на котором её меряют, не видел ни он, ни она.
- **Калибровка для замера обучается по фолдам,** на четырёх из пяти, как и в пайплайне. Она стоит около 1.9 пункта MAE - если обучить её на всём, кандидат получит фору больше той разницы, о которой gate вообще выносит решение.

Какому фолду принадлежит член ансамбля, манифест не записывает. Это **измеряется**, а не предполагается: энкодер хуже всего работает на фолде, который не видел, и пометки должны сложиться в перестановку. Если не сложились - прогон падает с матрицей ошибок вместо красивого числа.

Пакет, собранный из конфига эксперимента, так переобучить нельзя: у него член ансамбля - это энкодер, а не фолд. Тогда воркер строит кандидата прежним путём и пишет об этом в лог.

Прогон воркера дописывает новые фото в `configs/splits/folds.json`, поэтому после дообучения этот файл в git показывается изменённым. Так и задумано: фолд фотографии не меняется никогда, а манифест пакета хранит хэш того файла фолдов, которым его учили.

Точка входа - `PipelineTrainingRunner` в [`src/loadvision/ml/training/runner.py`](src/loadvision/ml/training/runner.py), её вызывают воркер сервиса и CLI. Рабочей папкой должен быть корень репозитория: манифест пакета записывает путь к файлу фолдов относительным.

## Когда сервис отказывается отвечать

Модель ответит числом на любую картинку - на серую стену, на лес, на снимок кабины. Поэтому
перед ответом сервис смотрит, насколько кадр вообще похож на то, на чём модель училась, и
держит две линии: от первой фото уходит оператору, от второй прогноз не показывается вовсе.

Обе линии **сервис ставит сам**, и ни одна не записана в конфиг расстоянием. У каждой модели
своя шкала: у одной 0.1 - это уже далеко, у другой 0.3 - ещё близко. Поэтому при загрузке
пакета сервис прогоняет через него четыре эталонных кадра, в которых заведомо нет кузова -
серый, тёмный, засвеченный и шум, - и запоминает, куда они попали. Вместе с порогом из манифеста
это даёт **полосу**: от края обучающих фото до «здесь кузова нет». Линии стоят долями полосы
(`configs/app.yaml`, раздел `review`), а доли переносятся между моделями, в отличие от
расстояний.

Замерено на пакете v4, доля 0 - край обучающих фото, 1 - пустые кадры:

| Что за кадр | Доля полосы | Что делает сервис |
|---|---|---|
| 307 отложенных фото конкурса | медиана -0.08, максимум **+0.05** | отвечает |
| загруженный кузов с чужой камеры | **+0.05** | просит проверить |
| загруженный багажник легковой | +0.14 | просит проверить |
| фото размыто до нечитаемости | +0.08...+0.30 | просит проверить |
| кузов, где створка закрывает обзор | +0.31 | просит проверить |
| кузов с мешками, снят ночью | +0.33 | просит проверить |
| тягач без прицепа | +0.49...+0.80 | прогноз не показывает |
| фургон с закрытыми дверями, фура и лес | +0.82...+0.98 | прогноз не показывает |
| шум, засвеченный, тёмный, серый кадр | +1.00...+1.07 | прогноз не показывает |

Идеального зазора между группами нет: самое необычное настоящее фото стоит на **+0.051**, а
ближайший чужой кадр - стоковый снимок загруженного кузова - на **+0.050**. Они перекрываются
на одну тысячную, и это честный предел метода: хорошо снятый чужой кузов для модели почти
неотличим от самого непривычного своего.

Черта на **0.04** ловит все двадцать чужих кадров и отправляет на проверку два настоящих фото
из 307. Такова цена, и она названа: 0.7% потока уходит человеку ради того, чтобы чужой кузов
не прошёл молча.

**Черту выбирает не человек, а скрипт.** `scripts/ood_line.py` берёт две папки:

- `--real` - фото, на которых сервис **обязан отвечать**. Это `data/test/images`: 307
  отложенных фотографий конкурса. Метки для них не нужны, нужно только расстояние. Брать
  обучающие фото нельзя - каждое из них лежит внутри набора, до которого расстояние и
  меряется, то есть оказывается своим же ближайшим соседом. Замерено на v4: 40 обучающих
  доходят до -0.050, а отложенные - до +0.051, и черта по обучающим встала бы на -0.02,
  отправляя на проверку около 6% потока.
- `--foreign` - фото, на которых сервис **обязан не отвечать молча**: `data/probe/foreign`,
  20 кадров. Их мы собрали сами, и они лежат в репозитории.

Четыре из двадцати воспроизводятся точно: серую заливку, тёмный и засвеченный кадры и шум
строит `ml/inference/unusable_frames.py` на фиксированном зерне, и это те же кадры, которыми
пакет меряет верхний конец своей полосы. Остальные шестнадцать найдены в интернете: тягачи без
прицепа, фургоны с закрытыми дверями и снятые сбоку, машины на дороге, лес без машины, чужие
кузова и легковые багажники. Заменяются любыми похожими - важно не конкретное фото, а что на
нём: транспорт без доступного обзора кузова либо сцена вовсе без кузова.

```bash
uv run python scripts/ood_line.py --package storage/models/v4 \
    --real data/test/images --foreign data/probe/foreign
```

На v4 он вернул **0.04**: все 20 чужих кадров пойманы, на проверку уходит 2 настоящих фото из
307, то есть 0.7% потока. Занимает
около двух минут на 300 фото: расстояние считается по эмбеддингу одного члена ансамбля, без
остальных четырёх, без карты глубины и без голов - число получается то же самое. На сам
инференс это не влияет: чтобы назвать процент, нужна вся модель.

Число фотографий в `--real` важно: черта ставится по хвосту их распределения, а хвост по два
десятка точек не оценивается. На случайных подвыборках из наших 307 черта по 20 фото в 84%
случаев оказывается ниже верной, по 100 - в 61%, и только все 307 дают её устойчиво.

Это не формальность. Доля не переносится между пакетами, хотя и выглядит безразмерной. На
пакете v5 та же черта пропускает кузов с мешками картошки, а черта, которая ловит его там,
отправила бы на проверку 57 фото из 307 здесь - 18.6% потока. Поэтому при смене пакета скрипт
запускается заново, до того как числу поверят.

Важное ограничение: расстояние говорит «незнакомо», а не «плохо». Хорошее фото с новой камеры
для модели так же ново, как испорченное, и одним числом их не разделить - поэтому в середине
сервис не решает, а спрашивает человека.

Чего линия не умеет - ловить фото, которое неприятно смотреть, но которое **типично**. Мы
взяли пять самых неудачных кадров датасета - вплотную снятые контейнеры, запотевший объектив,
ночную съёмку снаружи - и замерили. Они лежат на долях от -0.07 до +0.08, вокруг медианы
обычных фото (-0.08). Черту проходят четыре из пяти. Это ожидаемо: они из обучающей выборки,
то есть знакомы модели по построению, и их доля к тому же занижена - фото входит в тот самый
набор, до которого меряется расстояние.

Но и ловить их не нужно. На честной кросс-валидации модель ошиблась на этих пяти на 0, 15, 0,
5 и 5 пунктов - в среднем **5.00 против 5.76** по всему датасету. Кадр, неприятный человеку,
для модели чаще всего лёгкий. Больше того, единственный из пяти, который черта поймала, модель
угадала точно, а тот, где она ошиблась на 15, черту прошёл.

Отсюда честная формулировка того, что умеет сервис: он отличает **не наши данные**, а не
плохие фотографии. Это подтверждено зазором 0.44 между настоящими фото и чужими. Обещать
второе мы не стали: замер трёх дешёвых признаков - засвет, размытость, яркость - показал, что
на 10% помеченных они ловят 13-15% крупных промахов против 10% у случайного выбора. Это
неотличимо от случайности, и правила на этом мы не строим.

Проверить любой набор фотографий на текущей модели:

```bash
uv run python scripts/ood_scale.py <папка>     # --package storage/models/<версия>
```

Замер шкалы стоит около полутора секунд и кэшируется рядом с пакетом в `storage/models/<версия>.scale.json`;
новая модель считает его один раз. Замер привязан к сборке: в файле записаны устройство,
версия torch и платформа, и на другой сборке он считается заново. Две наши CPU-сборки дают
одно и то же - macOS 0.41879708 против linux в контейнере 0.41879696, - но на видеокарте
считает другое ядро, и переносить туда замер с процессора нельзя.

## Сверка с нормативным отчётом

Вместе с фото можно прислать загрузку из документов - элемент `DeclaredLoadPct` в запросе или
поле на странице оценки. Тогда ответ несёт и расхождение:

```xml
<LoadPct>85.3</LoadPct>
<Declared loadPct="30.0" deviation="55.3"/>
```

API отдаёт **число**, а не приговор: насколько далеко факт от документа, решает потребитель.
Страницы читают это число своим правилом и пишут «загружено больше (или меньше), чем по
документам». Если расхождение меньше 10 п.п., страницы молчат: столько же составляют собственная
ошибка модели (5.8) и разброс самих разметчиков (около 10), и вердикт на таком основании был бы
выдумкой.

## Оценка веса груза

Под фотографией есть блок «Вес груза». Оператор выбирает кузов и вид груза, сервис отвечает
вилкой и показывает, из чего она получена:

```
Объём груза   15.31 м³
Плотность     150-320 кг/м³
```

Вверху карточки появляются две строки - вес и габариты. Ответ сохраняется, поэтому число, по
которому человек принял решение, не меняется задним числом при правке таблицы плотностей.

**Почему выбирает человек, а не модель.** Фотография говорит только, какая доля пола занята.
Размер кузова с неё не снять: в кадре нет предмета известного размера, от которого считать
масштаб. Плотность груза - тем более. Поэтому кузов берётся из списка - **5, 10 и 20 тонн**,
те самые, что названы в условии задачи, плюс «иной габарит» с вводом трёх сторон.

**Честно о точности: её нет.** В датасете нет ни одного взвешивания, поэтому ни MAE, ни любой
другой метрики оценки веса не существует и быть не может. Мы это не скрываем, а обозначаем
прямо на странице: «оценка по типовой плотности, не взвешивание».

Плотности взяты не с потолка, а ограничены двумя публичными числами: почтовый роллтейнер
весит около 100 кг пустым и занимает примерно кубометр, а груз легче 160 кг/м³ в логистике
считается лёгким. Проверка на здравый смысл сходится с паспортами машин:

| кузов | объём | роллтейнеры при 100% | паспорт |
|---|---|---|---|
| 5 тонн | 36.5 м³ | 3281-7000 кг | 5000 кг |
| 10 тонн | 51.0 м³ | 4586-9784 кг | 10000 кг |
| 20 тонн | 90.0 м³ | 8097-17273 кг | 20000 кг |

Виды груза выведены из наших же фотографий: 128 кадров размечены руками, и основная единица
почтовой перевозки - сетчатый роллтейнер, которого в первоначальном списке не было. Разметка
лежит в [`docs/ml/labels/`](docs/ml/labels/). На ней же замерено, что вид груза предсказывается
по эмбеддингу с точностью 64% против 39% у «всегда самый частый класс», а высота штабеля - 80.5%
против 37.5%, ни разу не ошибаясь дальше соседней градации. Автоподстановку мы не включили:
сначала эту разметку должен проверить человек.

Оценка веса **не входит в прогноз**: XML-ответ не меняется, модель не вызывается, блок
открывается кнопкой.

## Что модель умеет и чего не умеет

**Сигналы доверия.** С каждым прогнозом сервис отдаёт неуверенность (разброс ответов пяти моделей) и непохожесть сцены на обучающие (расстояние до ближайших обучающих эмбеддингов). Как сервис решает, что с этим расстоянием делать, - в разделе «Когда сервис отказывается отвечать».

**Чего сервис намеренно не выставляет.** Признак `blurry` в схеме есть, но не выставляется: замер показал, что резкость не коррелирует с ошибкой вовсе. Показывать её значило бы врать пользователю. Признак `too_dark` выставляется по средней яркости кадра: порог 20 из 255, самое тёмное фото датасета имеет 21.6.

**Где ошибаемся больше всего.** Середина диапазона: MAE 9.33 при истинной загрузке 20-80 против 3.32 на почти пустых и 4.35 на почти полных. Это главная оставшаяся потеря.

**Предел разметки.** Метка - экспертная глазомерная оценка: 97% значений кратны 5, всего 24 различных значения на 716 фото. У почти неотличимых кадров одного кузова метки расходятся в среднем на 10 пунктов. Это значит, что текущие 5.76 лежат близко к неустранимому шуму разметки, и дальнейшее снижение MAE упирается не в архитектуру, а в данные.

**Масса груза** в XML-ответе не возвращается. Разметки массы в датасете нет, обучить её не на чем, а расчёт по объёму и плотности - это арифметика поверх прогноза, и он живёт на странице оценки: оператор выбирает кузов и вид груза, сервис отвечает вилкой (раздел «Оценка веса груза»). В API этого нет намеренно: значение зависит от двух чисел, которых нет в запросе.

## Воспроизводимость

- Фолды валидации зафиксированы в git (`configs/splits/folds.json`), у каждой модели они одни и те же.
- Манифест пакета хранит коммит сборки, хэш датасета, SHA-256 каждого файла пакета и файл фолдов, на котором посчитаны метрики.
- Кэш эмбеддингов подписан отпечатком препроцессинга: изменится нормализация, рамка или декодирование фото - кэш отвергается с внятным текстом, а не смешивает старые векторы с новыми.
- Обучение и сервис читают фотографии **одной и той же функцией** и готовят их **одним и тем же кодом**. Что пакет `baseline-v0` в точности повторяет отправку организаторов, держит тест `tests/quality/test_baseline_parity.py`.
- **Точного повторения отправки по хэшу у нас нет, и мы это измерили.** Прогон пакета v4 по 307 отложенным фото дал 305 совпадений из 307; два снимка разошлись на один шаг округления - 5 против 10 и 95 против 100. Оба лежат ровно на границе, а в конце цепочки стоит округление до 5, которое превращает разницу в тысячные доли в пять пунктов. На метрику это влияет не больше чем на 0.03 MAE, но «тот же файл по хэшу» сказать нельзя.
